\begin{abstract}
%\deleted{Schema mapping can be defined as the task of identifying equivalent or joinable tables across heterogeneous Database schema. In GraphQL, the corollary is identifying equivalent or joinable types in GraphQL schema in order to enable GraphQL schema generation and querying. Existing approaches focus on REST API sequencing within single paradigms or database schema matching focused on columns, leaving comprehensive schema mapping across different APIs unexplored. We introduce Map-Reflect, a self-reflection framework that performs schema mapping through iterative refinement. The approach uses domain-aware clustering, hierarchical schema organization, and multi-stage reflection to improve mapping accuracy. Evaluation on ToolBench REST APIs, multiple GraphQL collections, ITOps observability data, and an adapted Spider 1.0 dataset shows Map-Reflect significantly boosts accuracy on schema mapping tasks and joinability assessments. Map-Reflect framework also provides interpretable mapping rationales for human validation.}

We study many-to-many schema mapping, a setting where multiple source types/fields may correspond to overlapping targets and vice versa—cases that retrievers and single-chain API sequencers fail to disambiguate. Prior approaches use self-reflection where models critique their own output, but self-reflection lacks external grounding and models may reinforce their own errors. We introduce Map-Reflect, an \emph{induced reflection} framework that performs schema mapping through a two-phase approach: an initial greedy mapping followed by reflection induced by three external signals—neighbourhood graph validation, error analysis (LLM-as-judge, schema deployment, query execution), and uncertainty quantification. Our approach is schema-agnostic, applying uniformly to REST APIs, databases, and other structured schemas. Map-Reflect applies domain-aware clustering to bound candidate sets and runs multi-stage induced reflection to achieve comprehensive many-to-many coverage without spurious mappings. We evaluate on multiple datasets including new enterprise benchmarks for API and database schema mapping. Induced reflection consistently lifts accuracy over non-reflective baselines while remaining model-agnostic. The framework emits interpretable rationales through a wiki validated by business stakeholders for human-in-the-loop validation in enterprise settings.
\end{abstract}

\section{Introduction}
\label{sec:intro}
Organizations rely on diverse API ecosystems and databases that must be integrated for effective data access. Schema mapping---identifying equivalent entity types across different schemas---is critical for building unified data access layers where users query heterogeneous sources without knowledge of underlying schema differences. This capability is increasingly important for AI agents and tool-calling scenarios, where LLMs must select and invoke APIs across multiple services.

    \caption{Map-Reflect pipeline overview. A user utterance is processed through schema retrieval and a greedy MAP phase, then refined via three external signals in the REFLECT phase to produce many-to-many mappings.}
    \Description{Map-Reflect pipeline showing User Utterance flowing through Schema Retrieval, MAP Phase, REFLECT Phase with three signals (Neighbourhood Graph, Error Analysis, Uncertainty Quantification), and outputting Many-to-Many Mapping Set.}
    \label{fig:pipeline}
\end{figure}

Traditional approaches focus on database integration with column-level mapping, but enterprise environments require schema retrieval and multi-faceted mapping across both APIs and databases. For example, Site Reliability Engineers managing hybrid cloud environments must query across multiple observability platforms, each with distinct schemas. The complexity of mapping across these disparate systems creates significant overhead.

\paragraph{The Many-to-Many Challenge.}
Prior work on schema mapping focuses on one-to-one alignments or single-chain API sequencing. Real enterprise environments require \emph{many-to-many mappings} where multiple source types/fields correspond to overlapping target structures. For example, \texttt{Incident} from one system may correctly map to both \texttt{Alert} and \texttt{Event} in another. Greedy one-to-one mapping leaves too many elements unmapped, while naive approaches create spurious mappings that break query semantics.

%\deleted{Recent advances in tool calling with large language models show promise for API-related tasks. ToolLLM introduced the ToolBench dataset with a BERT-based neural API retriever while AnyTool leverages GPT-4's function calling with hierarchical API organization. These methods focus primarily on sequencing a single chain of calls; they do not address systematic alignment of schema elements across products. Further these approaches require expensive models like GPT-4, limiting practical applicability.}

Recent advances in tool calling with large language models show promise for API-related tasks. ToolLLM~\cite{toolllm} introduced the ToolBench dataset with a BERT-based neural API retriever while AnyTool~\cite{anytool} leverages GPT-4's function calling with hierarchical API organization and self-reflection. However, these methods focus on sequencing a single chain of calls; they do not address systematic alignment of schema elements across products. Critically, self-reflection mechanisms lack external grounding---the model critiques its own output without validation against external signals, potentially reinforcing errors. Further, these approaches require expensive models like GPT-4, limiting practical applicability.

Building a unified Data Access Layer requires mapping schemas across both APIs and databases. We address this challenge through experiments on API datasets (ITOpsGraph, NL2GQL, ToolBench) and database schemas (OMOP). Our ITOpsGraph benchmark provides schema mapping across heterogeneous enterprise APIs, featuring (i)~deeply nested type hierarchies, (ii)~domain-specific terminology where semantically equivalent concepts have different names, and (iii)~many-to-many mappings where a single source type correctly maps to multiple targets. Our wiki-based SME annotation provides continuous ground truth refinement.

%\deleted{We introduce Map-Reflect, a self-reflection framework that addresses these limitations through multiple complementary approaches. Map-Reflect identifies functionally equivalent APIs within API collections, generating multiple mapping alternatives for task completion. The framework handles GraphQL schemas that are built on top of REST APIs and Databases. The self-reflection mechanism creates iterative refinement where the model critiques initial mapping decisions and generates improved mappings.}

We introduce Map-Reflect, an \emph{induced reflection} framework that addresses these limitations through a two-phase approach. In the first \emph{Map} phase, we greedily find the best mapping for each source type and its fields. In the second \emph{Reflect} phase, we induce reflection using three external signals to achieve comprehensive many-to-many mapping: (1)~a \emph{neighbourhood graph} that validates mapping assumptions, (2)~\emph{error analysis} from LLM-as-judge evaluation, schema deployment, and query execution, and (3)~\emph{uncertainty quantification} to identify contested mappings. Unlike self-reflection, induced reflection is externally grounded, validating mappings against objective signals.

%\deleted{Our contributions are multi-faceted: (1) Map-Reflect, a self-reflection framework for schema mapping that uses domain-aware clustering and multi-stage reflection, (2) a novel Graph Neural Network baseline specifically designed for GraphQL schema mapping that treats the problem as link prediction, (3) an agentic workflow system that also includes tool calling, (4) automated API documentation enhancement for schema retrieval, (5) and a wiki based human validation of the generated schema mapping.}

Our contributions are: (1)~Map-Reflect, an induced reflection framework for many-to-many schema mapping using three external signals (neighbourhood graph, error analysis, uncertainty quantification), (2)~a two-phase architecture (greedy Map followed by induced Reflect) that addresses the coverage vs.\ precision tradeoff, (3)~a wiki-based human-in-the-loop system for continuous ground truth refinement with full provenance tracking, (4)~new enterprise benchmarks for API and database schema mapping (ITOpsGraph, NL2GQL, ToolBench, OMOP), and (5)~comprehensive evaluation demonstrating that induced reflection outperforms self-reflection and non-reflective baselines.


\section{Related Work}

ToolLLM \cite{toolllm} introduced the ToolBench dataset based on the APIs in RapidAPI Hub. ToolLLM includes an API Retriever that identifies relevant APIs given natural language instructions. It introduces solution path annotation by constructing API call chains using ChatGPT, and enhances reasoning through a depth-first search decision tree. AnyTool \cite{anytool} incorporates a self-reflection mechanism to improve reliability. Upon receiving a user query, the system proposes an initial solution evaluated for feasibility by GPT-4. However, AnyTool's self-reflection lacks external grounding---the model critiques its own output without validation against external signals such as type-system checks or uncertainty measures. This means models may reinforce their own errors. Furthermore, these approaches focus on API sequencing within single paradigms, overlooking schema mapping challenges.

\paragraph{Classical Schema Matching.} Schema matching has a long history in the database community. Cupid~\cite{madhavan2001generic} introduced a foundational framework combining linguistic, structural, and domain-specific similarity signals to produce weighted type correspondences, establishing the principle that no single signal is sufficient and that match quality improves when signals are combined. COMA~\cite{10.5555/1287369.1287422} extended this by building a flexible platform for composing multiple matchers and reusing match results from prior operations to improve future ones---an early precursor to iterative refinement. iMAP~\cite{dhamankar2004imap} pushed further by discovering complex semantic correspondences beyond simple one-to-one column matches, using search over a space of mapping expressions to find hidden relationships. Despite these advances, all three systems assume relatively flat relational or XML schemas and produce one-to-one or one-to-few correspondences, which limits their applicability to enterprise API schemas with deeply nested type hierarchies and genuine many-to-many relationships. Map-Reflect builds on the multi-signal intuition of these classical approaches but replaces hand-engineered combination rules with LLM-driven reasoning, and replaces static reuse with an externally grounded reflection loop capable of discovering and validating many-to-many correspondences that classical matchers were not designed to produce.

DynaMap \cite{mazilu2022schema} uses dynamic programming to explore mapping spaces, while embedding-based approaches \cite{hättasch2022its} apply word vectors for matching. SMUTF \cite{zhang2025smutf} combines tags, rule-based signals, and semantic embeddings using XGBoost classifiers. These engineered feature-based approaches struggle with contextual relationships and semantic nuances.

Retrieving APIs for the sequencing task is a well-known problem. \cite{li2023api} and \cite{patil2023gorilla} used text embedding based API retrievers while \cite{toolllm} used a method fine-tuned with curated API retrieval data. Using tools and frontier models for this retrieval step is expensive and not practical in real world applications, particularly when systems like AnyTool require multiple GPT-4 agents operating simultaneously. \cite{saha2024sequential} and \cite{mandal2024graph} discuss API sequencing. \cite{basu-etal-2024-api} introduced a corpora for training LLMs and \cite{patil2023gorilla} and \cite{abdelaziz2024granitefunctioncallingmodelintroducing} presented different approaches to function calling. \cite{mandal2024graph} proposed using an API Graph to guide the sequencing process. \cite{chen2024apigen} discusses API recommendation. \cite{moon2024api} presented API-miner which extracts APIs from the OpenAPI specifications and finds similar APIs to help design new APIs. \cite{song2023restgpt} introduced the RestBench dataset which consists of python-like function signatures. \cite{liang2024taskmatrix} discusses training foundation models to connect them to APIs to accomplish tasks.

Mapping API endpoints predates large language models. \cite{lu2017learning} tried to do API mapping by reading API documents. \cite{liu2023recommeding} uses a knowledge graph to recommend analogical APIs. \cite{shao2022cross} constructs an API documentation graph using Graph Neural Networks. 

Recent work leverages large language models for schema mapping. The Learned Schema Mapper (LSM) \cite{zhang2023schema} uses fine-tuned BERT encoders for metadata-based matching. The Magneto framework \cite{liu2024magneto} combines Small Language Models and LLMs, where SLMs generate candidates that LLMs rerank. ISResMat \cite{du2024in} fine-tunes pre-trained models for column representations. Newer approaches enhance LLMs with retrieval mechanisms, converting schemas to natural language descriptions. ReMatch \cite{sheetrit2024rematch} leverages retrieval-augmented LLMs, while GraphRAGToolFusion \cite{lumer2025graphragtoolfusion} combines knowledge graphs with vector-based retrieval. These approaches lack mechanisms for inducing reflection through external signals and do not address many-to-many schema mapping. Matchmaker \cite{matchmaker} introduced a compositional LLM program for schema matching with a zero-shot self-improvement mechanism. However, their experiments focus on healthcare datasets (MIMIC, Synthea), and their self-improvement mechanism lacks the external grounding signals that our induced reflection provides.

\paragraph{LLM-Based Many-to-Many Schema Matching.}
Two recent works address the many-to-many matching challenge most directly and deserve explicit positioning. LLMatch~\cite{wang2025llmatch} decomposes schema matching into three stages---schema preparation, table-candidate selection, and column-level alignment---and introduces a Rollup/Drilldown optimization strategy: a Rollup module consolidates semantically related columns into higher-order concepts, and a Drilldown module re-expands these concepts for fine-grained column mapping. This two-level abstraction produces many-to-many column correspondences and is evaluated on SchemaNet, a new enterprise benchmark across three domains. SCHEMORA~\cite{gungor2025schemora} takes a retrieval-first approach, enriching schema metadata and combining BM25 lexical retrieval with FAISS vector retrieval to identify candidate matches without exhaustive pairwise comparison or labeled training data. Evaluated on the MIMIC-OMOP benchmark, it establishes state-of-the-art HitRate@5 and HitRate@3, demonstrating that hybrid retrieval with metadata enrichment is a strong baseline for healthcare schema matching. Similarly, AnyTool~\cite{anytool} requires constructing an elaborate hierarchical API graph as a preprocessing step before any matching can occur, which imposes significant upfront engineering cost and makes adding new APIs a structural operation rather than a simple schema registration.

Map-Reflect differs from all three in a fundamental architectural choice: rather than restructuring the schema representation upfront (LLMatch's Rollup, AnyTool's API graph) or relying on retrieval quality to determine what gets matched (SCHEMORA's hybrid retrieval), Map-Reflect begins with a greedy one-to-one Map phase and then induces revision through three externally grounded signals---neighbourhood graph consistency, deployment and execution errors, and uncertainty quantification. This design has a practical consequence beyond accuracy: because Map-Reflect requires no elaborate preprocessing graph or schema transformation, adding a new API or database schema requires only parsing its specification and optionally enriching its field descriptions via RAG. The neighbourhood graph is populated incrementally from mapping output rather than constructed as a prerequisite. This makes Map-Reflect operationally lighter and more suitable for enterprise environments where schemas evolve continuously and new data sources are onboarded regularly. Additionally, Map-Reflect is schema-agnostic across REST APIs, GraphQL, and relational databases, whereas LLMatch and SCHEMORA target relational schemas specifically.

\paragraph{Positioning.} Map-Reflect targets schema-agnostic \emph{many-to-many} mappings with an \emph{induced reflection} loop driven by three external signals: neighbourhood graph validation, error analysis, and uncertainty quantification. Unlike self-reflection approaches (AnyTool, Matchmaker) where models critique their own output, induced reflection validates against external ground truth, enabling reliable many-to-many coverage without spurious mappings. Our approach applies uniformly to REST APIs, databases, and other structured schemas.


\section{Map-Reflect Framework}
\label{sec:mapreflect}

%\deleted{Map-Reflect employs a modular framework handling REST API specifications and GraphQL schemas separately with specialized techniques for each paradigm. The architecture consists of schema analysis with clustering, mapping generation, self-reflection refinement, and output integration. Given API specifications (OpenAPI for REST, SDL for GraphQL), Map-Reflect performs domain and structural analysis to create clusters.}

Map-Reflect employs a two-phase architecture designed to address the many-to-many mapping challenge. The first phase (Map) performs greedy one-to-one mapping, which is fast but leaves many elements unmapped and may create spurious mappings. The second phase (Reflect) induces reflection using three external signals to refine the initial mapping into comprehensive many-to-many coverage. Given API specifications (OpenAPI for REST, SDL for GraphQL), Map-Reflect performs domain and structural analysis to create clusters, then applies the two-phase mapping process.

Unlike GPT-4--centric tool agents, Map-Reflect is a service-oriented architecture whose components are invoked but never trained. A user utterance $u$ is processed in five stages. First, a context extractor splits $u$ into source and destination phrases by prompting a hosted chat model. Second, each phrase is embedded and queried against a Chroma vector index, yielding neighbourhoods $\mathcal{S}_{\mathrm{src}}$ and $\mathcal{S}_{\mathrm{dst}}$. Third, a reasoning call evaluates every pair in $\mathcal{S}_{\mathrm{src}}\times\mathcal{S}_{\mathrm{dst}}$, assigns a confidence $\gamma_0$, and produces justifications---this is the greedy Map phase. Fourth, the Reflect phase collects three external signals and induces reflection to refine mappings. Finally, mappings with scores below threshold $\tau$ are pruned, yielding many-to-many coverage.

\subsection{Induced Reflection Mechanism}

%\deleted{The self-reflection mechanism is Map-Reflect's key innovation. After generating initial mappings, the system engages in iterative self-critique where the LLM analyzes initial mapping decisions, identifies issues or inconsistencies, and generates improved mappings based on self-analysis. This process involves multiple refinement rounds with each iteration incorporating lessons from previous attempts.}

The induced reflection mechanism is Map-Reflect's key innovation. Unlike self-reflection where models critique their own output without external validation, induced reflection uses three external signals to ground the refinement process. This ensures that mappings are validated against objective evidence rather than the model's own potentially erroneous judgments.

%\deleted{Reflection can be triggered in three distinct ways. \textit{Self-reflection} fires unconditionally after the first proposal. \textit{Error-aware reflection} activates when a rule engine detects a type-system violation such as incompatible scalar kinds or missing mandatory arguments. \textit{Knowledge-graph reflection} is invoked when a lookup into a curated wiki returns an explicit synonym edge linking either the candidate types themselves or their ancestors.}

Reflection is induced by three external signals:

\textbf{Signal 1: Neighbourhood Graph Validation.} For each candidate mapping $(s, t)$, we retrieve k-nearest neighbours from the Neo4j graph populated from schema mapping output. We validate assumptions by checking: Do neighbours of source type also map to neighbours of target type? Are there alternative targets in the neighbourhood with similar structure? Are there unmapped neighbours that should be included? If neighbourhood evidence contradicts the greedy mapping assumption, we add alternative mappings (achieving many-to-many) or remove inconsistent ones.

\textbf{Signal 2: Error Analysis.} We collect error signals from three sources at different stages of the pipeline:

\textit{(i) Initial Ranking Error Detection.} Before reflection, we analyze the greedy mapping's initial ranking to detect specific error patterns that indicate the top prediction may be wrong:
\begin{itemize}
    \item \textbf{Source/Target Product Mismatch}: If the top-ranked candidate belongs to the source product rather than the target product, the model matched by name similarity instead of finding the semantic equivalent in the target schema. This is a critical error---the model confused which direction to map.
    \item \textbf{Foreign Key Misalignment}: For fields ending in \texttt{\_id} that reference another table (e.g., \texttt{concert\_stadium\_id}), we verify the prediction maps to the primary key of the referenced table (e.g., \texttt{stadium.id}), not to another foreign key in the source table.
    \item \textbf{Name Similarity Without Semantic Match}: When the top prediction has high lexical overlap with the source field but the model's reasoning mentions ``name'', ``similar'', or ``match'', we flag this as potentially superficial matching that ignores semantic meaning.
    \item \textbf{Type Mismatch Indicators}: If field names contain type hints (e.g., \texttt{\_string}, \texttt{\_int}, \texttt{\_date}) and the source and target type hints disagree, we flag potential type incompatibility.
    \item \textbf{Low Confidence Warning}: When the top prediction's confidence score falls below 0.6, we flag high uncertainty requiring careful review.
    \item \textbf{Ambiguous Top Predictions}: When the top two candidates have scores within 0.1 of each other, the model cannot confidently distinguish them, signaling ambiguity.
\end{itemize}
Detected errors are passed to the reflection prompt with explicit instructions to address each error pattern, encouraging the model to revise its ranking based on semantic meaning rather than superficial similarity.

\textit{(ii) LLM-as-Judge Evaluation.} After initial mapping, an LLM-as-judge evaluates semantic equivalence and joinability of proposed mappings, providing an independent assessment of mapping quality.

\textit{(iii) Schema Deployment and Query Execution.} We attempt to generate and deploy a unified GraphQL schema, revealing type conflicts and missing fields. GraphQL query execution runs test queries against the generated schema, where null results indicate unmapped fields and type mismatches indicate bad mappings.

Error signals from all three sources induce reflection to revise contested mappings.

\textbf{Signal 3: Uncertainty Quantification.} We measure prediction entropy over candidate mappings. High uncertainty indicates the model is unsure about the correct target—often signaling that multiple targets are valid (many-to-many). High-uncertainty mappings trigger reflection to explore alternative mappings that the greedy phase missed.

Let $\gamma_r(s,t)$ be the confidence after reflection round $r$. Given an adjustment $\Delta_r(s,t)$ constrained to $[-1,1]$, scores are updated as
\[
\gamma_{r+1}(s,t)=\operatorname{clip}(\gamma_r(s,t)+\eta\,\Delta_r(s,t),0,1),
\]
where $\eta$ is a step size and $\Delta_r$ aggregates signals from neighbourhood validation, error analysis, and uncertainty quantification. The mapping set returned to the user is $\{(s,t,j,\gamma)\mid\gamma\ge\tau\}$ after convergence.

\subsection{Two-Phase Architecture: Map and Reflect}

\textbf{Phase 1: Map (Greedy One-to-One).} For each GraphQL type $T_s$ in the source schema, we compute embedding similarity with all types in the target schema and select the highest-scoring target type $T_t$ as the initial mapping. For each field $F_s$ in the mapped source type, we similarly select the best matching field $F_t$. This produces a fast one-to-one mapping with confidence scores, but leaves many types/fields unmapped and may create spurious mappings based on superficial similarity.

\textbf{Phase 2: Reflect (Induced Many-to-Many Refinement).} The Reflect phase transforms the greedy one-to-one mapping into comprehensive many-to-many coverage: (1)~\emph{Coverage analysis} identifies unmapped source and target elements, (2)~\emph{Signal collection} gathers neighbourhood validation, error analysis, and uncertainty scores, (3)~\emph{Induced reflection} explores alternative mapping targets for unmapped or high-uncertainty elements, and (4)~\emph{Spurious mapping removal} verifies all one-to-many mappings and removes those that fail validation.

\subsection{Schema-Agnostic Mapping}

Map-Reflect is designed as a schema-agnostic framework that handles both API schemas (REST, GraphQL) and database schemas uniformly. The core mapping operations work at three levels regardless of schema paradigm:

\textbf{Type-level mapping} identifies semantically equivalent entities across schemas—whether they are GraphQL types, REST API resources, or database tables. For example, \texttt{VirtualMachine} in one system may map to \texttt{EC2Instance} in another.

\textbf{Field-level mapping} matches individual attributes within mapped types---whether GraphQL fields, REST parameters, or database columns. Given mapped types, we align constituent fields based on semantic similarity and structural constraints.

\textbf{Relationship preservation} ensures that mapped schemas maintain semantic integrity. If \texttt{VirtualMachine} contains \texttt{Host} in the source, the mapped target types should preserve this containment relationship.

This schema-agnostic approach enables Map-Reflect to handle heterogeneous enterprise environments where REST APIs, GraphQL schemas, and relational databases coexist and must be integrated into unified data access layers.

\subsection{ITOpsGraph Knowledge Structure}

ITOpsGraph organizes schema knowledge in a hierarchical structure designed to support both retrieval and validation during mapping.

\subsubsection{Products}
Top-level entities representing distinct systems or APIs (e.g., Turbonomic, Instana, AWS). Each product contains multiple types.

\subsubsection{Types (Tables)}
Schema entities within products—GraphQL types, REST resources, or database tables. Types contain fields and have relationships with other types.

\subsubsection{Fields (Columns)}
Atomic schema elements within types. Fields have names, descriptions, and data types.

\subsubsection{Documents and Chunks}
Product documentation (PDF manuals, API references) is parsed and chunked into segments indexed in ChromaDB. We have 26,643 documentation chunks across 239MB of source material. These chunks provide RAG-based context enrichment for sparse schema descriptions.

\subsubsection{RAG-Based Documentation Enrichment}
Schema descriptions from API specifications are often sparse or missing. We implement a Retrieval-Augmented Generation (RAG) pipeline to enrich field descriptions: (1) product documentation is converted to text and chunked into segments, (2) chunks are embedded and indexed in ChromaDB collections, (3) for each field, we retrieve the top-k most relevant chunks based on field name and context, and (4) an LLM generates concise two-line descriptions combining the field's original metadata with retrieved documentation context. This pipeline produces 11,110 RAG-enhanced descriptions that improve semantic matching during the Map phase.

\subsubsection{Concepts}
Abstract semantic categories (e.g., ``compute resource'', ``monitoring metric'', ``alert'') that group related types across products. Concepts enable cross-product discovery and validation.

\subsubsection{Neighbourhood Graph Construction}
The neighbourhood graph is a property graph built from the unified schema to enable structure-aware candidate expansion during mapping. We construct the graph using NetworkX with three node types and weighted edges:

\textbf{Graph Construction.} For each property in the schema catalogue, we create a node with attributes: \texttt{id} (fully qualified name like \texttt{turbonomic\_Action.actionID}), \texttt{type} (the parent type), \texttt{product} (source system), and \texttt{description} (RAG-enhanced text). Edges connect properties that share structural relationships:
\begin{itemize}
    \item \textbf{Same-type edges}: Properties within the same type are connected with weight 0.3, capturing intra-type cohesion.
    \item \textbf{Cross-type edges}: Properties across types within the same product are connected with weight 0.7, enabling discovery of related concepts.
    \item \textbf{Semantic edges}: Properties with high embedding similarity ($>0.8$) across products are connected with weight based on similarity score.
\end{itemize}

\textbf{Candidate Expansion.} During the Map phase, after retrieving initial candidates via embedding similarity, we expand the candidate set using $k$-hop neighbourhood traversal (default $k=5$). For each retrieved candidate $c$, we add its neighbours $\mathcal{N}_k(c)$ to the candidate pool, weighted by path distance. This expansion serves two purposes: (1) it surfaces semantically related fields that may not have high lexical similarity with the source field, and (2) it provides structural context for the reflection phase to validate mapping assumptions.

The ITOpsGraph neighbourhood graph contains 11,110 nodes (one per field) and over 26 million edges. Graph construction takes approximately 80 seconds on commodity hardware. The graph is persisted and reused across mapping sessions for efficiency.

\textbf{Validation During Reflection.} The Neo4j graph stores the same structural relationships for persistent querying. During induced reflection, we traverse this graph to validate mapping assumptions: if \texttt{VirtualMachine} maps to \texttt{EC2Instance}, do neighbours of \texttt{VirtualMachine} also map to neighbours of \texttt{EC2Instance}? Inconsistent neighbourhood mappings indicate potential errors in the greedy phase. The neighbourhood graph provides Signal~1 (neighbourhood validation) during the Reflect phase.

\subsection{Human in the Loop}

Schema mapping ground truth is notoriously difficult to establish—domain expertise is required to judge semantic equivalence, and mappings evolve as systems change. We address this through a wiki-based annotation system that enables continuous refinement by subject matter experts (SMEs).

\subsubsection{Wiki Architecture}
We deploy a MediaWiki instance organized hierarchically by product, type, and field. Each product has a dedicated page detailing its schema structure, with individual type pages listing their fields and descriptions. Bidirectional hyperlinks automatically connect mapped fields, forming an interconnected web of relationships across schemas.

\subsubsection{Annotation Workflow}
The annotation process operates in four stages:

\begin{enumerate}
    \item \textbf{Auto-population}: Schema mapping output generates wiki pages with type definitions, field descriptions, and proposed cross-product mappings. Each page includes schema definitions and RAG-enhanced descriptions.

    \item \textbf{SME Validation}: Subject matter experts review auto-generated mappings in the wiki interface. Experts correct errors, add missing relationships, and annotate edge cases with justifications.

    \item \textbf{Iterative Refinement}: As new products are added or methods improve, the wiki is updated and re-validated. Better mappings improve the wiki, and validated content becomes ground truth for future methods.

    \item \textbf{Ground Truth Extraction}: Validated mappings are exported to create evaluation datasets. The wiki's edit history provides provenance for how ground truth evolves.
\end{enumerate}

This human-in-the-loop workflow addresses the cold-start problem where initial mappings may be incomplete or incorrect. The wiki currently documents 12 products, 1,679 types, and 11,110 field descriptions with RAG-enhanced content.


\section{Experiments}

We compare Map-Reflect against five baseline approaches. The Traditional Schema Mapping Toolkit (SMT) represents classical rule-based methods relying on string similarity, structural analysis, and domain-specific rules implementing edit distance calculations, structural matching algorithms, and pattern-based field alignment strategies. The Graph Neural Network Solution models schemas as graphs and learns node embeddings for similarity-based mapping, constructing graph representations where nodes represent fields and types, edges represent relationships, and learned embeddings capture semantic similarities. AnyTool represents hierarchical retrieval with GPT-4 function calling and self-reflection, adapted for schema mapping by organizing schemas into domain-specific clusters and leveraging GPT-4's reasoning capabilities. ReAct represents a reasoning and acting baseline that interleaves reasoning traces with actions. MatchMaker~\cite{matchmaker} is a compositional LM program featuring a zero-shot self-improvement mechanism using ColBERT-v2 for candidate retrieval and iterative refinement. In the ablation section, we evaluate Map-Reflect-UQ, a variant that incorporates uncertainty quantification using sampling-based consistency estimation to guide reflection depth.

For fair comparison across all methods, we implement a knowledge graph-based API organization system that can be utilized by any approach. This knowledge graph, structured as a wiki, contains hierarchical relationships between API categories, tools, and individual endpoints, populated through systematic analysis of API documentation and schema structures. The knowledge graph provides a standardized foundation for API discovery and organization, ensuring that performance differences reflect methodological innovations rather than data organization advantages. All baseline methods, including Map-Reflect, have access to this knowledge graph during their respective retrieval and mapping processes.

Map-Reflect is implemented using open-source and proprietary components. Vector indexing utilizes Milvus for similarity search while core mapping logic employs LLM models. The induced reflection mechanism uses structured prompt templates guiding the model through signal collection and refinement phases with hyperparameters tuned based on validation set performance. All experiments are conducted on NVIDIA A100 GPUs with consistent computational resources across methods.

We evaluate all methods using two primary LLMs:
\begin{itemize}
    \item \textbf{Granite-4} (\texttt{ibm/granite-4-h-small}): IBM's Granite 4 model, a smaller model for schema mapping tasks.
    \item \textbf{Llama-3.3-70B} (\texttt{meta-llama/llama-3-3-70b-instruct}): Meta's Llama 3.3 70B instruction-tuned model, providing stronger reasoning capabilities.
\end{itemize}
Both models are accessed via WatsonX. In the tables, ``Granite'' refers to Granite-4 and ``Llama'' refers to Llama-3.3-70B. For fair comparison, all LLM-based baselines (ReAct, AnyTool, MatchMaker) use these same model versions; the original AnyTool paper~\cite{anytool} used GPT-4, but we re-implement with Llama-3.3-70B and Granite-4 to isolate methodological differences. MatchMaker additionally uses ColBERT-v2~\cite{colbert} (\texttt{colbert-ir/colbertv2.0}) for candidate retrieval. For reproducibility, all LLM calls use temperature$=$0 and a fixed random seed (42).

We evaluate Map-Reflect on API and database schema mapping datasets representing diverse real-world scenarios:

\subsection{Evaluation Metrics}

We evaluate schema mapping using two complementary metrics that capture both API-level selection and field-level mapping quality.

\textbf{API-Level (Product) Accuracy} measures whether the method correctly identifies the source and target schemas. A mapping is API-correct if predicted source and target match expected schemas (case-insensitive):
\begin{equation}
\text{API Acc.} = \frac{|\{s : \text{pred}(s) = \text{exp}(s)\}|}{|\text{Samples}|}
\end{equation}

\textbf{Field-Level F1 (Given Correct API)} measures property mapping quality \emph{only on samples where API selection was correct}, isolating field mapping quality from API selection errors. We compute precision, recall, and their harmonic mean:
\begin{equation}
P = \frac{|\text{Pred} \cap \text{GT}|}{|\text{Pred}|}, \quad
R = \frac{|\text{Pred} \cap \text{GT}|}{|\text{GT}|}, \quad
\text{F1} = \frac{2 \cdot P \cdot R}{P + R}
\end{equation}
where Pred and GT are the sets of predicted and ground-truth field mappings across all API-correct samples.

For semantic assessment, we use cosine similarity with sentence-transformer embeddings (threshold 0.3) and an LLM-as-judge that scores mappings on equivalence and joinability (threshold 0.5). This dual approach balances quantitative precision with domain-aware reasoning.

\subsection{Evaluation Modes: Oracle vs Retrieval}

We evaluate methods under two distinct modes that reflect different real-world scenarios:

\textbf{Oracle Mode (Target Given).} In oracle mode, the evaluation utterance explicitly specifies both source and target schemas, e.g., ``\textit{map turbonomic Action.actionID to concert PackageRecommendation.recommendation\_id}.'' This mode isolates the field-level mapping capability from schema retrieval, enabling fair comparison with prior work like MatchMaker~\cite{matchmaker} that assumes the target schema is known. Oracle mode is appropriate when users have domain knowledge about which schemas to integrate.

\textbf{Retrieval Mode (Target Discovery).} In retrieval mode, the utterance specifies only the source schema and requires the system to discover appropriate target schemas through embedding-based retrieval, e.g., ``\textit{find types that can be mapped to cloudability StringFilterInput}.'' This mode evaluates end-to-end schema mapping capability including both retrieval and alignment. Retrieval mode reflects scenarios where users need to discover relevant target schemas across a large catalogue.

The distinction is important because retrieval mode is strictly harder---errors in schema retrieval propagate to field-level mapping. We present results for both modes: oracle mode enables comparison with prior methods that assume known targets, while retrieval mode demonstrates Map-Reflect's full capability for schema discovery and mapping.

\section{Discussion}
\label{sec:discussion}

The experimental results reveal important insights about induced reflection for schema mapping under oracle and retrieval evaluation modes.

\subsection{Oracle vs.\ Retrieval Mode Analysis}

\subsubsection{Oracle Mode Performance}
When the target schema is given (oracle mode), Map-Reflect achieves 98.1\% API accuracy and 76.6\% field F1 on ITOpsGraph with Llama-3.3-70B, demonstrating strong field alignment capability. On OMOP datasets in oracle mode, Map-Reflect achieves perfect API accuracy (100\%) across all three variants, with field F1 ranging from 41.4\% (CMS) to 81.2\% (Synthea). Map-Reflect outperforms MatchMaker on Synthea (+10.9pp) and MIMIC (+4.6pp). These oracle mode results enable fair comparison with prior work like MatchMaker~\cite{matchmaker} that assumes the target schema is known.

MatchMaker demonstrates strong cross-dataset performance in oracle mode, achieving 95.2\% API accuracy on ITOpsGraph, 42.1\% on NL2GQL, and 89.5--100\% on OMOP with Llama-3.3-70B. Notably, MatchMaker achieves the best field-level F1 on NL2GQL (83.2\% with Granite-4) and CMS (48.9\% with Llama-3.3-70B), outperforming other methods on these datasets. ReAct achieves 87.6\% API accuracy on ITOpsGraph but produces no field-level predictions in the current implementation.

\subsubsection{Retrieval Mode Challenges}
Retrieval mode presents additional challenges: the system must first discover appropriate target schemas from a catalogue using embedding-based retrieval. Errors in schema retrieval propagate to field-level mapping, making retrieval mode strictly harder than oracle mode in the general case.

\textbf{Why 100\% API accuracy is achievable in retrieval mode.} The retrieval mode API accuracy of 100\% on ITOpsGraph and OMOP (Table~\ref{tab:api_accuracy_retrieval}) reflects dataset characteristics rather than trivial retrieval. ITOpsGraph contains only 12 products in the target pool; given a source utterance with strong embedding similarity, the retrieval top-$k$ reliably includes the correct target. OMOP datasets have a single fixed target schema (the OMOP CDM), so retrieval reduces to confirming the source schema against a known target. These constrained pools make API-level retrieval tractable even when field-level mapping remains challenging.

\textbf{Field F1 inversion: retrieval (80.1\%) vs oracle (76.6\%).} Counter-intuitively, retrieval mode achieves higher field F1 than oracle mode on ITOpsGraph. This inversion arises from evaluation set differences: retrieval mode evaluates only samples where embedding-based retrieval successfully identifies the target schema, which biases toward schema pairs with stronger semantic alignment. Oracle mode includes all ground-truth pairs, including cross-paradigm mappings (GraphQL to Protocol Buffer) where structural mismatches cause field-level failures regardless of retrieval. The retrieval pre-filter thus selects ``easier'' pairs where field-level mapping is more tractable. This selection bias means retrieval mode field F1 is not directly comparable to oracle mode; future work should evaluate on identical sample sets to isolate retrieval effects.

The results reveal a counterintuitive finding: \emph{reflecting on fewer fields yields better accuracy}. The optimal threshold (0.15) triggers reflection on only 4\% of fields, achieving 88.7\% accuracy (+0.2pp over base). Lower thresholds that trigger more reflections (e.g., 0.08 with 47\% coverage) provide no improvement, as the additional reflections introduce noise that cancels out the benefit. This suggests that UQ-based reflection should be highly selective, targeting only the most uncertain predictions where the model is genuinely confused between candidates.

\subsection{Induced Reflection Benefits}

Map-Reflect validates our hypothesis that induced reflection with uncertainty quantification strengthens schema mapping. The three reflection signals serve complementary roles: neighbourhood graphs validate structural assumptions, error analysis catches semantic and deployment issues, and uncertainty quantification identifies contested mappings that require deeper exploration.

\textbf{Error Detection Effectiveness.} The initial ranking error detection mechanism (Section~3.1, Signal~2) provides targeted guidance for reflection. When the detector identifies a source/target product mismatch---where the top prediction belongs to the source schema rather than the target---it generates an explicit error message instructing the model to find the semantic equivalent in the correct target schema. This addresses a common failure mode where models match by name similarity across the wrong direction. Similarly, foreign key misalignment detection catches cases where \texttt{table\_foreign\_id} fields are mapped to the wrong table's primary key. The reflection prompt incorporates detected errors with semantic matching rules:
\begin{itemize}
    \item Foreign keys should map to the \emph{primary key} of the referenced table, not to another foreign key
    \item Match the \emph{target} entity, not the source entity
    \item Verify fields represent the \emph{same data}, not just similar names
\end{itemize}
When errors are detected or uncertainty is high, the reflection prompt explicitly instructs the model: ``Assume the \#1 candidate is likely incorrect if errors were detected. Be bold---your initial answer is likely wrong.'' This aggressive prompting overcomes the model's tendency to confirm its initial prediction.

The stakeholder-validated wiki provides an additional benefit beyond mapping accuracy: interpretable rationales for human-in-the-loop validation. Business stakeholders can review and refine mappings, with validated mappings becoming ground truth for future induced reflection.

\textit{Continuous Ground Truth Improvement.} The ITOpsGraph wiki enables a novel evaluation paradigm where ground truth evolves alongside method improvements. When a new schema mapping method produces better results on a subset of types, SMEs can validate those improvements in the wiki, which then become part of the ground truth for future evaluations. This addresses a fundamental limitation of static benchmarks: as methods improve beyond the original ground truth quality, fixed benchmarks become less discriminative. Our wiki-based approach ensures the benchmark grows with the state of the art.

The integration between schema mapping code and the wiki is bidirectional: (i) mapping output populates the wiki with proposed relationships, and (ii) validated wiki content is extracted as ground truth for evaluation. This tight coupling ensures consistency between the knowledge graph used for induced reflection and the evaluation benchmark.

\subsection{Error Analysis of Field-Level Failures on ITOpsGraph}
Map-Reflect achieves 98.1\% API accuracy on ITOpsGraph but only 76.6\% field accuracy, meaning that even when the correct source--target type pair is identified, roughly one in four fields is not correctly mapped. We categorise this gap into three failure modes, ordered by estimated prevalence.

\textbf{Semantic synonym misses (estimated \textasciitilde{}55\% of failures).} ITOpsGraph contains many cases where semantically equivalent fields carry entirely different names across products---for example, a field named \texttt{severity} in one product and \texttt{criticalityLevel} in another, or \texttt{hostName} versus \texttt{nodeIdentifier}. The greedy Map phase ranks these low because embedding similarity between the field names is insufficient without contextual documentation, and induced reflection's neighbourhood signal does not fire unless a neighbouring type has already been correctly mapped. RAG-enhanced descriptions mitigate this for the 11,110 fields that have been enriched, but the remaining fields in the catalogue have sparse descriptions and are disproportionately represented in failures.

\textbf{Schema paradigm boundary failures (estimated \textasciitilde{}30\% of failures).} ITOpsGraph spans both GraphQL and Protocol Buffer schemas. Fields that are modelled as nested object types in GraphQL (e.g., \texttt{VirtualMachine.resourceAllocation.cpuMhz}) appear as flat repeated fields in Protocol Buffer definitions. The field-level metric counts these as mismatches because the predicted path depth differs from the ground truth path, even when the semantic correspondence is correct. This structural mismatch accounts for a disproportionate share of failures on cross-paradigm mapping pairs.

\textbf{Many-to-many boundary disagreements (estimated \textasciitilde{}15\% of failures).} For types such as \texttt{Alert}, \texttt{Incident}, and \texttt{Event}---which the paper identifies as legitimate many-to-many mapping targets---SME-validated ground truth includes multiple valid target fields. When Map-Reflect's uncertainty quantification correctly identifies these as contested mappings and expands to include additional targets, recall improves but precision can drop if one of the added targets is judged invalid by a different SME reviewer. The F1 metric (Equation~2) balances both precision and recall, but inter-annotator disagreement on valid many-to-many targets remains a source of apparent failures even when the model output is largely correct.

Together these three categories suggest that the primary bottleneck is not the induced reflection mechanism itself---which demonstrably improves field accuracy by 6.0 percentage points over the no-UQ baseline on ITOpsGraph---but rather sparse field documentation for uncommon schema elements and the structural impedance mismatch between GraphQL and Protocol Buffer representations. Enriching documentation coverage and adopting a path-normalisation step before field-level evaluation are the most direct remedies for closing the remaining gap.

\section{Conclusion}

We introduced Map-Reflect, an induced reflection framework for many-to-many schema mapping that uses three external signals (neighbourhood graph validation, error analysis, uncertainty quantification) rather than self-reflection. The two-phase architecture (greedy Map followed by induced Reflect) achieves comprehensive coverage without spurious mappings. In oracle mode, Map-Reflect achieves 98.1\% API accuracy and 76.6\% field F1 on ITOpsGraph, and perfect API accuracy (100\%) across all OMOP datasets with field F1 up to 81.2\% on Synthea. Map-Reflect outperforms MatchMaker on ITOpsGraph (+4.4pp), OMOP\_Synthea (+10.9pp), and OMOP\_MIMIC (+4.6pp) for field-level F1. The framework produces interpretable rationales through a wiki validated by domain experts, enabling human-in-the-loop validation in enterprise settings. Future work includes extending induced reflection to multi-hop mapping across federated schemas and improving schema retrieval to close the gap between oracle and retrieval modes.
