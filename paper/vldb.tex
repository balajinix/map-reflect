\begin{abstract}
%\deleted{Schema mapping can be defined as the task of identifying equivalent or joinable tables across heterogeneous Database schema. In GraphQL, the corollary is identifying equivalent or joinable types in GraphQL schema to enable GraphQL schema generation and querying. Existing approaches focus on REST API sequencing within single paradigms or database schema matching focused on columns, leaving comprehensive schema mapping across different APIs unexplored. We introduce Map-Reflect, a self-reflection framework that performs schema mapping through iterative refinement. The approach uses domain-aware clustering, hierarchical schema organization, and multi-stage reflection to improve mapping accuracy. Evaluation on ToolBench REST APIs, multiple GraphQL collections, ITOps observability data, and an adapted Spider 1.0 dataset shows Map-Reflect significantly boosts accuracy on schema mapping tasks and joinability assessments. Map-Reflect framework also provides interpretable mapping rationales for human validation.}

Schema mapping is the task of aligning database tables, API endpoints, and GraphQL types together with their fields across heterogeneous schema. It is a prerequisite for data federation, function calling, and agentic tool composition. Existing approaches for schema mapping either require expensive offline pre-processing or rely on unconditional self-reflection that lacks external grounding and hence can make the same mistakes in reflection. We introduce Map-Reflect, an \emph{induced reflection} framework that addresses both these problems. Our framework includes a greedy Map phase that produces an initial mapping and a Reflect phase that selectively refines it using externally grounded signals like uncertainty quantification, error analysis, and neighborhood graph. Map-Reflect is schema-agnostic and works with REST APIs, GraphQL, and relational databases. It supports runtime target discovery without any elaborate offline pre-processing and runs with open source models. Evaluated on five benchmarks spanning enterprise API schema and relational databases, it outperforms baselines, and incorporates human-in-the-loop validation.
\end{abstract}

\section{Introduction}
\label{sec:intro}
Organizations rely on diverse API ecosystems and databases that must be integrated for effective data access. Schema mapping~\cite{matchmaker, liu2024magneto, sheetrit2024rematch, buss2025scalableschemamappingusing}, is the task of identifying equivalent entity types across different schemas, and is critical for building unified data access layers that allow querying across heterogeneous sources without knowledge of the underlying schema differences. This matters for AI agents and tool-calling scenarios~\cite{wang2024llmagent}, where LLMs must select and invoke APIs across multiple services.

\begin{figure}[!t]
    \centering
    \includegraphics[width=0.9\columnwidth]{intro_diagram.png}
    \caption{Map-Reflect pipeline: greedy MAP followed by signal-driven REFLECT.}
    \Description{Map-Reflect pipeline showing User Utterance flowing through Schema Retrieval, MAP Phase, REFLECT Phase with three signals (Neighbourhood Graph, Error Analysis, Uncertainty Quantification), and outputting Many-to-Many Mapping Set.}
    \label{fig:pipeline}
\end{figure}

Traditional approaches focus on database integration with column-level mapping, but enterprise environments require schema retrieval and multi-faceted mapping across both APIs and databases. For example, Site Reliability Engineers managing hybrid cloud environments must query across multiple observability platforms, each with distinct schemas. Mapping across these disparate systems creates substantial overhead.

\paragraph{The Many-to-Many Challenge.}
Prior work on schema mapping focuses on one-to-one alignments~\cite{matchmaker, sheetrit2024rematch} or single-chain API sequencing~\cite{saha-etal-2024-sequential}. Real enterprise environments require \emph{many-to-many mappings} where multiple source types/fields correspond to overlapping target structures. For example, \texttt{Incident} from one system may correctly map to both \texttt{Alert} and \texttt{Event} in another. Greedy one-to-one mapping leaves too many elements unmapped, while naive approaches create spurious mappings that break query semantics. Many Large Language Models (LLM) based solutions for this problem use reflection. A key challenge for any reflection mechanism is knowing \emph{when} to reflect: firing unconditionally corrupts correct predictions, while a reliable trigger must identify genuinely uncertain cases. Uncertainty quantification provides this gate. As we show on diverse datasets, UQ-triggered reflection is the only trigger that does not reduce field recall; all other signals fire too broadly and over-correct predictions that were already correct.

Recent advances in tool calling with large language models show promise for API-related tasks. ToolLLM~\cite{toolllm} and AnyTool~\cite{anytool} focus on sequencing a single chain of calls; they do not address systematic alignment of schema elements across products, which is the prerequisite for variable mapping between function calls. Sequential function calling with variable mapping across APIs has been studied by~\citet{saha-etal-2024-sequential}, who introduce GraphQLRestBench and demonstrate that GraphQL schema representations are effective for encoding API response structure in LLM prompts for multi-step API sequencing. Self-reflection mechanisms in these approaches lack external grounding because the model critiques its own output without validation against external signals, potentially reinforcing errors~\cite{huang2024selfcorrect}. Further, AnyTool requires GPT-4, limiting practical applicability.

\paragraph{The Pre-processing Cost Problem.}
Schema inventories in enterprise deployments are never static: Data Fabric and Data Mesh implementations~\cite{blohm2024data,dehghani2022datamesh} grow through M\&A activity and SaaS onboarding; Backend for Frontend patterns~\cite{richardson2018microservices} require re-alignment every time a new upstream service is added; and agentic code tools such as Claude Code and Gemini CLI need schema mapping as a \emph{runtime} capability rather than a batch offline step. AnyTool~\cite{anytool} requires rebuilding a multi-vector index, a DSPy bootstrapping loop, and a three-tier agent hierarchy whenever schemas change, and reports 43.3 GPT-4 calls per query in its original setting. In our problem setting, we want to avoid such expensive pre-processing steps and also the dependence on frontier models.

Building a unified Data Access Layer (DAL) or a Common Data Model requires mapping schemas across both APIs and databases. Hence we evaluate on API datasets (ITOpsGraph, NL2GQL, ToolBench) and database schemas (OMOP, SchemaNet). Our ITOpsGraph benchmark provides schema mapping across heterogeneous enterprise APIs, featuring (i)~deeply nested type hierarchies, (ii)~domain-specific terminology where semantically equivalent concepts have different names, and (iii)~many-to-many mappings where a single source type correctly maps to multiple targets. Our wiki-based Subject Matter Expert (SME) annotation provides continuous ground truth refinement.

We introduce Map-Reflect, an \emph{induced reflection} framework that addresses the above limitations through a two-phase approach (Figure~\ref{fig:pipeline}). In the first \emph{Map} phase, we greedily find the best mapping for each source type and its fields. In the second \emph{Reflect} phase, we explore three candidate external signals to induce reflection: a \emph{neighbourhood graph} that validates mapping assumptions, \emph{error analysis} from LLM-as-judge evaluation, schema deployment, and query execution, and \emph{uncertainty quantification} that selectively targets genuinely ambiguous predictions. As the ablation in Section~\ref{sec:ablation} shows, only the UQ signal avoids degrading accuracy; the other two hurt by over-correcting correct predictions. Besides empirical evidence, we provide theoretical grounding for UQ as a reflection trigger based in the consistency hypothesis~\cite{xiao2025consistency} and SIMBA~\cite{simba2025}. Unlike AnyTool, which requires building a static GPT-4--driven three-tier hierarchy before any mapping can be performed, Map-Reflect operates with open-source medium-sized models (Llama-3.3-70B, Granite-4-small) and supports both oracle mode and retrieval mode, discovering target schemas at query time from a live catalog with no offline pre-processing.

Our contributions are as follows:
\begin{itemize}[noitemsep,topsep=2pt,leftmargin=*]
  \item \textbf{Map-Reflect}, a two-phase induced reflection framework for schema-agnostic, GPT-free schema mapping across REST APIs, GraphQL, and relational databases, with ablation showing UQ-triggered reflection is the only signal that avoids degrading accuracy (Section~\ref{sec:ablation}).
  \item \textbf{Retrieval mode}: lightweight hybrid retrieval (dense + BM25) enables runtime target discovery from a live catalogue with no offline preprocessing or model retraining, a capability no other evaluated baseline provides.
  \item \textbf{ITOpsGraph benchmark}: a new enterprise API schema mapping benchmark covering 12 products, 11,110 RAG-enriched fields, and SME-validated ground truth, enabling evaluation of many-to-many mapping across heterogeneous GraphQL and proto buffer schemas.
\end{itemize}


\section{Related Work}

\paragraph{Classical Schema Matching.} Cupid~\cite{madhavan2001generic}, COMA~\cite{10.5555/1287369.1287422}, and iMAP~\cite{dhamankar2004imap} are representative systems from the classical schema matching literature~\cite{rahm2001survey}, combining linguistic, structural, and domain-specific similarity. However, these systems assume flat relational schemas and produce one-to-one correspondences, limiting applicability to nested API schemas with many-to-many relationships. Valentine~\cite{koutras2021valentine} provides a systematic benchmark comparing these techniques. Map-Reflect builds on multi-signal intuition but uses LLM-driven reasoning with externally grounded reflection.

DynaMap~\cite{mazilu2022schema} and SMUTF~\cite{zhang2025smutf} use dynamic programming and XGBoost classifiers respectively, but struggle with contextual relationships. API retrieval and sequencing have been addressed by embedding-based retrievers~\cite{li2023api,patil2023gorilla}, fine-tuned methods~\cite{toolllm}, graph-based approaches~\cite{mandal2024graph}, and GraphQL-based sequential function calling~\cite{saha-etal-2024-sequential}. Pre-LLM API mapping work includes document-based~\cite{lu2017learning}, knowledge graph~\cite{liu2023recommeding}, and GNN approaches~\cite{shao2022cross}.

    \label{fig:reflection_example}
\end{figure*}

ToolLLM~\cite{toolllm} introduced the ToolBench dataset with an API Retriever for natural language instructions. Toolformer~\cite{schick2023toolformer} shows that LLMs can learn to invoke tools via self-supervised training, motivating tool-use settings where schema mapping becomes necessary. AnyTool~\cite{anytool} incorporates self-reflection for reliability via a three-tier agent hierarchy (meta-agent $\rightarrow$ category-agents $\rightarrow$ tool-agents) built around RapidAPI's static category taxonomy, and is designed around GPT-4 function calling. The hierarchy cannot be transferred to a new API corpus without rebuilding the taxonomy from scratch. AnyTool's self-reflection has no external validation signals, which can reinforce errors~\cite{huang2024selfcorrect}. These approaches focus on API sequencing, not schema mapping.

\paragraph{LLM-Based Schema Mapping.} LSM~\cite{zhang2023schema} uses fine-tuned BERT encoders; Magneto~\cite{liu2024magneto} combines SLMs with LLM reranking; ReMatch~\cite{sheetrit2024rematch} and GraphRAGToolFusion~\cite{lumer2025graphragtoolfusion} add retrieval mechanisms. MatchMaker~\cite{matchmaker} introduced compositional LLM programs with zero-shot self-improvement via synthetic in-context demonstrations, but requires GPT-4 as backbone, targets only flat relational schemas, and relies on offline ColBERT-v2 multi-vector indexing plus DSPy~\cite{khattab2023dspy} bootstrapping before deployment, preprocessing costs that scale with schema size and must be repeated when schemas evolve. For many-to-many matching, LLMatch~\cite{wang2025llmatch} uses Rollup/Drilldown abstraction, while SCHEMORA~\cite{gungor2025schemora} combines BM25 and FAISS~\cite{johnson2019billion} retrieval. Both target relational schemas and require upfront schema restructuring.

\paragraph{Uncertainty Quantification for LLMs.}
Uncertainty quantification (UQ) approaches estimate the reliability of LLM outputs
and are increasingly recognised as essential for trusted AI systems~\cite{simba2025}.
An important category are \emph{black-box} methods, which rely only on model outputs
without internal access and are therefore robust to model upgrades and compatible with
proprietary APIs~\cite{xiao2025consistency,simba2025}.
A central line of black-box work uses generation \emph{consistency} as a proxy for
confidence: when a generated response is more different from others it is more likely
to be incorrect, so responses that are consistently similar are more likely to be
correct~\cite{lin2024generating,manakul2023selfcheck}.
Xiao et al.~\cite{xiao2025consistency} formalize this as the
\emph{consistency hypothesis}, introducing three statistical statements
(Sim-Correct, Sim-Separate, Sim-Any) and empirically verifying them across 8
benchmarks spanning QA, summarisation, and text-to-SQL.
The \emph{text-to-SQL} task, which is the closest analogue to schema field prediction, shows the strongest and most consistent signal across all three hypothesis variants.
Bhattacharjya et al.~\cite{simba2025} introduce SIMBA, a
Similarity-Based Aggregation framework that unifies and generalises consistency-based
UQ by viewing confidence as a learned or hand-designed function of pairwise
similarities between generations.
SIMBA demonstrates that classification over pairwise similarities (using random forests)
yields the best-calibrated confidence estimates, while the harmonic mean of similarities
outperforms the arithmetic mean for structured-output tasks.
Map-Reflect's UQ trigger is grounded directly in this framework: we use generation
consistency to detect when field mapping predictions are genuinely ambiguous and
selectively invoke reflection only for those fields.

\paragraph{Positioning.} Map-Reflect begins with greedy one-to-one mapping and explores three external signals for induced reflection. Retrieval is intentionally lightweight, using hybrid dense vector search~\cite{karpukhin2020dpr} and BM25~\cite{robertson2009probabilistic} lexical matching merged by Reciprocal Rank Fusion~\cite{cormack2009reciprocal}, because the Reflect phase corrects residual rank errors rather than requiring retrieval to be perfect. Of the three signals, only UQ-triggered reflection avoids degrading accuracy (Section~\ref{sec:ablation}), compared to AnyTool's unconditional self-reflection~\cite{anytool} which has no external validation. Map-Reflect is schema-agnostic across REST APIs, GraphQL, and relational databases, and we evaluate on both API corpora (ITOpsGraph, NL2GQL, ToolBench) and database schema benchmarks (OMOP, SchemaNet). New schemas require only parsing and optional RAG enrichment, with no graph construction, model training, or schema restructuring.


\section{Map-Reflect Framework}
\label{sec:mapreflect}

%\deleted{Map-Reflect employs a modular framework handling REST API specifications and GraphQL schemas separately with specialized techniques for each paradigm. The architecture consists of schema analysis with clustering, mapping generation, self-reflection refinement, and output integration. Given API specifications (OpenAPI for REST, SDL for GraphQL), Map-Reflect performs domain and structural analysis to create clusters.}

Our two-phase architecture is designed for the many-to-many mapping challenge. The first phase (Map) performs greedy one-to-one mapping, which is fast but leaves many elements unmapped and may create spurious mappings. The second phase (Reflect) explores three candidate external signals for induced reflection: neighbourhood graph validation, error analysis, and uncertainty quantification. As the ablation in Section~\ref{sec:ablation} establishes, only UQ-triggered reflection should be used by default. Given API specifications or database schemas, Map-Reflect performs domain and structural analysis to create clusters, then applies the two-phase mapping process.

Unlike GPT-4-centric tool agents, our components are invoked but never trained. A user utterance $u$ is processed in five stages. First, a context extractor splits $u$ into source and destination phrases by prompting a hosted chat model. Second, each phrase is embedded and queried against a Chroma vector index, yielding neighbourhoods $\mathcal{S}_{\mathrm{src}}$ and $\mathcal{S}_{\mathrm{dst}}$. Third, a reasoning call evaluates every pair in $\mathcal{S}_{\mathrm{src}}\times\mathcal{S}_{\mathrm{dst}}$, assigns a confidence $\gamma_0$, and produces justifications; this is the greedy Map phase. Fourth, the Reflect phase collects three external signals and induces reflection to refine mappings. Finally, mappings with scores below threshold $\tau$ are pruned, yielding many-to-many coverage.

\subsection{Two-Phase Architecture: Map and Reflect}

\textbf{Phase 1: Map (Greedy One-to-One).} For each source type $T_s$ in the source schema, we compute embedding similarity with all types in the target schema and select the highest-scoring target type $T_t$ as the initial mapping. For each field $F_s$ in the mapped source type, we similarly select the best matching field $F_t$. This produces a fast one-to-one mapping with confidence scores, but leaves many types/fields unmapped and may create spurious mappings based on superficial similarity.

\textbf{Phase 2: Reflect (Uncertainty-Guided Refinement).} The Reflect phase selectively refines the greedy mapping using external signals: \emph{coverage analysis} identifies unmapped source and target elements, \emph{signal collection} gathers neighbourhood validation, error analysis, and uncertainty scores, \emph{induced reflection} explores alternative mapping targets for high-uncertainty elements, and \emph{spurious mapping removal} verifies one-to-many mappings and removes those that fail validation. Our ablation (Section~\ref{sec:ablation}) shows that of the three signals, only UQ-triggered reflection avoids degrading accuracy; error-based and neighbourhood-based signals fire too broadly, over-correct correct predictions, and are not recommended in the default configuration.

\subsection{Induced Reflection Mechanism}

%\deleted{The self-reflection mechanism is Map-Reflect's key innovation. After generating initial mappings, the system engages in iterative self-critique where the LLM analyzes initial mapping decisions, identifies issues or inconsistencies, and generates improved mappings based on self-analysis. This process involves multiple refinement rounds with each iteration incorporating lessons from previous attempts.}

Induced reflection refines mappings using external signals rather than model self-critique alone (Figure~\ref{fig:reflection_example}).

%\deleted{Reflection can be triggered in three distinct ways. \textit{Self-reflection} fires unconditionally after the first proposal. \textit{Error-aware reflection} activates when a rule engine detects a type-system violation such as incompatible scalar kinds or missing mandatory arguments. \textit{Knowledge-graph reflection} is invoked when a lookup into a curated wiki returns an explicit synonym edge linking either the candidate types themselves or their ancestors.}

We induce reflection via three external signals:

\textbf{Signal 1: Neighbourhood Graph Validation.} For each candidate mapping $(s, t)$, we retrieve $k$-nearest neighbours from the graph store and validate whether neighbours of the source type also map to neighbours of the target type, whether alternative targets with similar structure exist, and whether any unmapped neighbours should be included. If neighbourhood evidence contradicts the greedy mapping, we add alternative mappings (achieving many-to-many coverage) or remove inconsistent ones.

\textbf{Signal 2: Error Analysis.} We collect error signals from three sources at different stages of the pipeline:

\textit{(i) Initial Ranking Error Detection.} Before reflection, we analyse the greedy mapping's ranking to detect six error patterns: source/target product mismatch (top candidate belongs to the source product rather than the target); foreign key misalignment (a field ending in \texttt{\_id} maps to a foreign key rather than the referenced primary key); name similarity without semantic match (high lexical overlap but reasoning that mentions ``name'' or ``similar''); type hint mismatch (\texttt{\_string}/\texttt{\_int}/\texttt{\_date} suffixes disagree); low confidence (top score below 0.6); and ambiguous top-2 predictions (scores within 0.1 of each other). Detected patterns are passed to the reflection prompt with explicit instructions to revise rankings based on semantics rather than superficial similarity.

\textit{(ii) LLM-as-Judge Evaluation.} After initial mapping, an LLM-as-judge~\cite{zheng2023judging} evaluates semantic equivalence and joinability of proposed mappings, providing an independent assessment of mapping quality.

\textit{(iii) Schema Deployment and Query Execution.} We attempt to generate and deploy a unified schema from the predicted mappings, revealing type conflicts and missing fields. Executing test queries against the generated schema surfaces null results (unmapped fields) and type mismatches (bad mappings).

Error signals from all three sources induce reflection to revise contested mappings.

\textbf{Signal 3: Uncertainty Quantification.}
Selective reflection requires knowing \emph{which} predictions are genuinely uncertain
rather than firing unconditionally.
The consistency hypothesis~\cite{xiao2025consistency} provides formal
justification: correct LLM generations are systematically more similar to other
generations than incorrect ones, a pattern that holds especially strongly for
structured-output tasks analogous to schema field prediction.
SIMBA~\cite{simba2025} operationalises this as a family of aggregation functions over
pairwise similarities between generations.

\textbf{UQ trigger (entropy-H).}
Let $\{\gamma_1,\dots,\gamma_n\}$ be the LLM-assigned confidence scores for the top-$n$
candidate field predictions produced in the MAP phase for a source field $f$.
We compute Shannon entropy $H = -\sum_j \gamma_j \log \gamma_j$ and trigger reflection
when $H > \tau_H$, where $\tau_H$ is tuned on a held-out validation split of ITOpsGraph.
High entropy indicates dispersed confidence across candidates. Correct predictions tend to concentrate on one candidate, while uncertain predictions spread across multiple plausible targets. Entropy is a single-pass proxy for the generation-consistency signal in SIMBA~\cite{simba2025}.

High-uncertainty mappings trigger reflection to explore alternative mapping
targets that the greedy MAP phase missed, often because multiple targets are
semantically valid (many-to-many coverage opportunity).

\paragraph{Grounding.}
Xiao et al.~\cite{xiao2025consistency} show that correct LLM generations are more similar to each other than incorrect ones, with the effect strongest on structured-output tasks. SIMBA~\cite{simba2025} generalises this by aggregating pairwise generation similarities into calibrated confidence estimates. Our entropy-H trigger approximates this: high entropy (dispersed confidence) identifies the low-consistency regime where predictions are most likely to be wrong. The ablation (Table~\ref{tab:ablation_components}) confirms that error-based and neighbourhood signals reduce field F1 by 7--15\,pp, while UQ-triggered reflection does not.

Let $\gamma_r(s,t)$ be the confidence after reflection round $r$. Given an adjustment $\Delta_r(s,t)$ constrained to $[-1,1]$, scores are updated as
\begin{equation}
\gamma_{r+1}(s,t)=\operatorname{clip}(\gamma_r(s,t)+\eta\,\Delta_r(s,t),0,1),
\label{eq:update}
\end{equation}
where $\eta{=}0.1$ is a fixed step size. $\Delta_r(s,t)\in[-1,0]$ is negative when a signal fires and zero otherwise: the neighbourhood signal sets $\Delta_r = -(g - 0.2)$ when the neighbourhood consistency gap $g$ exceeds 0.2; the error signal sums per-error penalties (source/target mismatch $-0.40$, foreign-key misalignment $-0.30$, low confidence $-0.10$, ambiguous top-2 $-0.10$); and the UQ signal sets $\Delta_r = -(H - 0.5)$ when prediction entropy $H > 0.5$. Mappings with scores below $\tau$ are pruned; the final output is $\{(s,t,j,\gamma)\mid\gamma\ge\tau\}$ with pruning threshold $\tau{=}0.5$.

\subsection{Schema-Agnostic Mapping}

Map-Reflect is a schema-agnostic framework that handles REST, GraphQL, and database schemas uniformly. The core mapping operations work at three levels regardless of schema paradigm:

\textbf{Type-level mapping} identifies semantically equivalent entities across schemas, including GraphQL types, REST API resources, and database tables. For example, \texttt{VirtualMachine} in one system may map to \texttt{EC2Instance} in another.

\textbf{Field-level mapping} matches individual attributes within mapped types, including GraphQL fields, REST parameters, and database columns. Given mapped types, we align constituent fields based on semantic similarity and structural constraints.

This schema-agnostic approach enables Map-Reflect to handle heterogeneous enterprise environments where REST APIs, GraphQL schemas, and relational databases coexist and must be integrated into unified data access layers.

\subsection{Neighbourhood Graph Construction}
The neighbourhood graph is a property graph built from the unified schema to enable structure-aware candidate expansion during mapping. We construct the graph using NetworkX~\cite{hagberg2008networkx} with a single node type and three weighted edge types:

\textbf{Graph Construction.} For each property in the schema catalogue, we create a node with attributes: \texttt{id} (fully qualified name), \texttt{type} (parent type), \texttt{product} (source system), and \texttt{description} (enriched text). Three edge types connect properties: same-type edges (weight 0.3) connect properties within the same type; cross-type edges (weight 0.7) connect properties across types within the same product; and semantic edges connect properties across products with high embedding similarity ($>0.8$), weighted by similarity score.

\textbf{Candidate Expansion.} During the Map phase, after retrieving initial candidates via embedding similarity, we expand the candidate set using $k$-hop neighbourhood traversal ($k{=}5$, chosen empirically on a held-out ITOpsGraph validation subset). For each retrieved candidate $c$, we add its neighbours $\mathcal{N}_k(c)$ to the candidate pool, weighted by path distance, surfacing semantically related fields and providing structural context for the reflection phase.

Graph construction scales linearly with schema size; for ITOpsGraph (11,110 fields), construction takes approximately 80 seconds on commodity hardware. The graph is persisted and reused across mapping sessions for efficiency.

\textbf{Validation During Reflection.} The graph store persists structural relationships for querying during induced reflection. We traverse the graph to validate mapping assumptions: if \texttt{TypeA} maps to \texttt{TypeB}, do neighbours of \texttt{TypeA} also map to neighbours of \texttt{TypeB}? Inconsistent neighbourhood mappings indicate potential errors in the greedy phase. The neighbourhood graph provides Signal~1 (neighbourhood validation) during the Reflect phase.

\subsection{Human in the Loop}

Schema mapping ground truth is notoriously difficult to establish because domain expertise is required to judge semantic equivalence and mappings evolve as systems change. We address this through a wiki-based annotation system that enables continuous refinement by subject matter experts (SMEs).

\subsubsection{Wiki Architecture}
We deploy a MediaWiki~\cite{mediawiki} instance organized hierarchically by product, type, and field. Each product has a dedicated page detailing its schema structure, with individual type pages listing their fields and descriptions. Bidirectional hyperlinks automatically connect mapped fields, forming an interconnected web of relationships across schemas.

\subsubsection{Annotation Workflow}
Our annotation process operates in four stages. Schema mapping output first auto-populates wiki pages with type definitions, field descriptions, and proposed cross-product mappings. SMEs then review and correct errors, add missing relationships, and annotate edge cases with justifications. As new products are added or methods improve, the wiki is updated and re-validated so that better mappings improve the wiki and validated content becomes ground truth. Finally, validated mappings are exported as evaluation datasets with full provenance via the wiki's edit history.

This workflow addresses the cold-start problem: initial mappings may be incomplete, and the wiki provides a structured path to iterative refinement. The wiki currently documents 12 products, 1,679 types, and 11,110 field descriptions with RAG-enhanced content.


\section{Experiments}

We compare Map-Reflect against three baseline approaches. The GNN baseline models schemas as graphs~\cite{kipf2017gcn} using a two-layer Graph Convolutional Network with 128-dimensional embeddings. Nodes represent types and fields; edges encode same-type (weight~0.3), cross-type (weight~0.7), and embedding-similarity (weight by score) relationships, identical to the neighbourhood graph in Section~\ref{sec:mapreflect}. The model is trained on ITOpsGraph training pairs using binary cross-entropy with a 5:1 negative-to-positive sampling ratio and evaluated zero-shot on all other datasets. AnyTool~\cite{anytool} represents hierarchical retrieval with GPT-4 function calling and self-reflection. In the original paper, AnyTool organises 16K+ RapidAPI APIs into a static three-tier taxonomy (meta-agent $\rightarrow$ category-agents $\rightarrow$ tool-agents) and issues an average of 43.3 GPT-4 calls per query. We adapt it for schema mapping by organising schemas into domain-specific clusters; however, AnyTool's self-reflection lacks external grounding and its hierarchy must be rebuilt whenever new schemas are added. MatchMaker~\cite{matchmaker} is a compositional LM program for relational database schema matching featuring a zero-shot self-improvement mechanism using ColBERT-v2 for candidate retrieval and iterative refinement. The original paper uses GPT-4 exclusively and evaluates only on flat relational schemas (MIMIC, Synthea); it does not handle nested API schemas or many-to-many mappings. The pipeline requires two offline preprocessing steps before deployment: (i) building a ColBERT-v2 multi-vector document index, and (ii) running a DSPy~\cite{khattab2023dspy} bootstrapping loop that executes the full pipeline on evaluation examples to generate synthetic in-context demonstrations. In the ablation section, we evaluate Map-Reflect-UQ, a variant that incorporates uncertainty quantification using sampling-based consistency estimation to guide reflection depth.

\textbf{Omitted Baselines.} We do not compare against SCHEMORA~\cite{gungor2025schemora}, a recent many-to-many schema matching method that targets flat relational schemas and requires upfront column-group normalization that assumes tabular input with explicit primary/foreign key annotations. Our benchmarks include deeply nested API schemas where this restructuring step does not apply, and SCHEMORA's code release is pending. We include MatchMaker~\cite{matchmaker} because it has public code and evaluation on the same OMOP and SchemaNet benchmarks. LLMatch~\cite{wang2025llmatch} reports SchemaNet results using field-level F1; Table~\ref{tab:schemanet} includes these numbers alongside our own results for reference, with the caveat that field F1 and type F1 are not directly comparable across methods.

Map-Reflect uses Milvus~\cite{wang2021milvus} for vector indexing and LLM calls for core mapping logic. Hyperparameters are tuned on a held-out validation split. All experiments run on NVIDIA A100 GPUs with the same computational budget across methods.

We evaluate all methods using two LLMs: \textbf{Granite-4} (\texttt{ibm/granite-4-h-small})~\cite{granite2025}, a smaller model, and \textbf{Llama-3.3-70B} (\texttt{meta-llama/llama-3-3-70b-instruct})~\cite{grattafiori2024llama3}, providing stronger reasoning.
Both models are accessed via WatsonX~\cite{ibm2023watsonx}. In the tables, ``Granite'' refers to Granite-4 and ``Llama'' refers to Llama-3.3-70B. For fair comparison, all LLM-based baselines (AnyTool, MatchMaker) use these same model versions; the original AnyTool paper~\cite{anytool} used GPT-4, but we re-implement with Llama-3.3-70B and Granite-4 to isolate methodological differences. MatchMaker also uses ColBERT-v2~\cite{colbert} (\texttt{colbert-ir/colbertv2.0}) for candidate retrieval. The original MatchMaker paper uses GPT-4 (0613) at temperature~0.5; our reimplementation uses the same Llama-3.3-70B and Granite-4 backbones as all other baselines. For reproducibility, all LLM calls use temperature$=$0 and a fixed random seed (42).

\subsection{Datasets}

We evaluate Map-Reflect on API and database schema mapping datasets representing diverse real-world scenarios:

\textbf{ToolBench Dataset}: We utilize the ToolBench dataset containing 49,937 REST APIs across 10,388 tools spanning 50 categories. For evaluation, we process the first 10,000 training queries and retain the 3,190 queries that involve at least two distinct APIs with overlapping parameter types, forming API mapping examples where each query-API pair generates variable mappings depending on functional similarities detected by the model. Queries involving only a single API (no cross-API mapping) are excluded.

\textbf{ITOpsGraph Dataset}: ITOpsGraph is generated by parsing GraphQL~\cite{graphql2021spec} schema from six observability products (Instana, Turbonomic, Concert, Cloudability, NS1, Watsonx-Orchestrate) and proto buffer~\cite{google2023protobuf} definitions from five cloud infrastructure tools (AWS, Azure, GCP, HashiCorp Terraform, HashiCorp Packer), yielding 1,640 types and 10,876 fields across 12 products. Product documentation (239\,MB of PDF manuals) is converted via docling~\cite{auer2024docling} and indexed in ChromaDB~\cite{chromadb2023} to generate RAG-enriched~\cite{lewis2020retrieval} descriptions; the enrichment process discovers an additional 234 fields referenced in documentation but absent from the parsed schemas, bringing the total to 11,110 RAG-enriched field descriptions. The unified schema is loaded into a typed property graph, and each type is documented in MediaWiki for SME validation. ITOpsGraph poses three challenges across its 521 evaluation samples: (i)~many-to-many mappings where \texttt{VirtualMachine} maps to both \texttt{EC2Instance} and \texttt{AzureVM}, (ii)~schema paradigm heterogeneity (GraphQL and proto buffer), and (iii)~domain-specific terminology where semantically equivalent fields carry different names (e.g., \texttt{Alert} vs \texttt{Incident} vs \texttt{Event}).

\textbf{NL2GQL Dataset}~\cite{kesarwani-etal-2024-graphql}: Natural language to GraphQL API schema mapping dataset featuring e-commerce, social media, and content management system schemas. The dataset contains 437 mapping instances with varying complexity levels from simple field mappings to complex relationship transformations, testing systems' ability to handle domain-specific terminology across 54 GraphQL API schemas.

\textbf{OMOP Datasets}: We evaluate on three healthcare database schema mapping benchmarks derived from the OMOP Common Data Model~\cite{omop,garza2016omop,hripcsak2015ohdsi}: (i) \textbf{CMS} (Centers for Medicare \& Medicaid Services claims data), (ii) \textbf{MIMIC}~\cite{johnson2016mimic} (Medical Information Mart for Intensive Care), and (iii) \textbf{Synthea}~\cite{walonoski2018synthea} (synthetic patient data). These datasets test mapping between proprietary healthcare data formats and the standardized OMOP schema, featuring challenges such as vocabulary mapping (ICD codes~\cite{who2019icd10} to SNOMED~\cite{snomed2021}), temporal alignment, and cardinality differences. Unlike API mapping, database schema mapping involves relational constraints and referential integrity.

\textit{Ground Truth Protocol.} The OMOP ground truth mappings are derived from the OMAP benchmark~\cite{matchmaker}, which provides expert-curated field-level correspondences between source schemas (CMS, MIMIC, Synthea) and the OMOP CDM target schema. Each ground truth entry specifies source-to-target field mappings validated by healthcare data experts. We evaluate OMOP datasets primarily in \textbf{oracle mode}, where both source and target schemas are specified in the utterance (e.g., ``map MIMIC PATIENTS to OMOP PERSON''). This follows the evaluation protocol of prior work~\cite{matchmaker} and reflects the typical use case where healthcare organizations know they want to map their proprietary data to the OMOP standard. Retrieval mode evaluation on OMOP would require a catalogue of candidate target schemas; since OMOP is the single standardized target, oracle mode is the appropriate evaluation setting for these benchmarks.

\textbf{Spider Dataset}~\cite{yu2018spider}: We derive a schema mapping benchmark from Spider~1.0, a text-to-SQL dataset containing 166~databases with expert-defined foreign key relationships. Each foreign key defines a joinable column pair between two tables; we extract all 745~unique table pairs (793~field-level mappings) across 164~databases as evaluation samples. Unlike other benchmarks that provide mapping utterances, Spider's ground truth is structural (foreign keys), testing whether methods can discover joinability from schema structure alone. The mapping utterance is generated as ``map~\texttt{<source\_table>}~data to~\texttt{<target\_table>}~data.'' Spider is the largest and most diverse relational benchmark in our evaluation, spanning domains including music, flights, pets, cars, healthcare, and education.

\textbf{SchemaNet Dataset}~\cite{wang2025llmatch}: A relational database schema matching benchmark covering seven schema pairs of varying complexity (377 total mappings): bank1\_bank2, imdb\_sakila, and five OMOP target pairs (cms\_omop, mimic\_iii\_omop, synthea\_omop, cprd\_gold\_omop, cprd\_aurum\_omop~\cite{herrett2015cprd}). The OMOP pairs overlap structurally with our OMOP evaluation but use different source schemas and ground truth; results are therefore reported separately. SchemaNet tests purely relational schema alignment without API or graph paradigms, providing complementary coverage to the API-focused benchmarks.

\subsection{Evaluation Metrics}

We evaluate schema mapping using two complementary metrics that capture both API-level selection and field-level mapping quality (Figure~\ref{fig:api_field_gap} visualises the gap between them across all methods and datasets).

\textbf{API-Level (Product) Accuracy} measures whether the correct source and target schemas are identified by the method. A mapping is API-correct if predicted source and target match expected schemas (case-insensitive):
\begin{equation}
\text{API Acc.} = \frac{|\{s : \text{pred}(s) = \text{exp}(s)\}|}{|\text{Samples}|}
\end{equation}

\textbf{Field-Level F1 (Given Correct API)} measures property mapping quality \emph{only on samples where API selection was correct}, isolating field mapping quality from API selection errors. We compute precision, recall, and their harmonic mean:
\begin{equation}
P = \frac{|\text{Pred} \cap \text{GT}|}{|\text{Pred}|}, \quad
R = \frac{|\text{Pred} \cap \text{GT}|}{|\text{GT}|}, \quad
\text{F1} = \frac{2 \cdot P \cdot R}{P + R}
\end{equation}
where Pred and GT are the sets of predicted and ground-truth field mappings across all API-correct samples.

For semantic assessment, we use cosine similarity with sentence-transformer embeddings~\cite{reimers2019sentence} (threshold 0.3) and an LLM-as-judge~\cite{zheng2023judging} that scores mappings on equivalence and joinability (threshold 0.5). The judge is a separately-invoked instance of Llama-3.3-70B at temperature~1.0 (vs.\ temperature~0 for the generator) with a distinct system prompt; it receives only the mapping output and field descriptions, not the generator's intermediate reasoning chain, mitigating confirmation bias. Together they provide both lexical precision and domain-aware semantic judgement. Because all generator calls use temperature~0 and seed~42, LLM results are fully deterministic; observed variance across datasets reflects dataset composition rather than stochastic inference.

\textbf{Efficiency.} Map-Reflect issues 3--5 LLM calls per source field in the base configuration: one MAP reasoning call, one REFLECT call per field where the UQ gate fires, and one LLM-as-judge call per type-level mapping. AnyTool reports 43.3 GPT-4 calls per query in its original setting~\cite{anytool}. The UQ gate ensures reflection is invoked only on uncertain fields; on NL2GQL, where the model is uniformly confident, zero reflection calls are made.

\subsection{Evaluation Modes: Oracle vs Retrieval}

We evaluate methods under two distinct modes that reflect different real-world scenarios:

\textbf{Oracle Mode (Target Given).} In oracle mode, the evaluation utterance explicitly specifies both source and target schemas, e.g., ``\textit{map turbonomic Action.actionID to concert PackageRecommendation.recommendation\_id}.'' This mode isolates the field-level mapping capability from schema retrieval, enabling fair comparison with prior work like MatchMaker~\cite{matchmaker} that assumes the target schema is known. Oracle mode is appropriate when the integration target is known in advance.

\textbf{Retrieval Mode (Target Discovery).} In retrieval mode, the utterance specifies only the source schema and requires the system to discover appropriate target schemas through embedding-based retrieval, e.g., ``\textit{find types that can be mapped to cloudability StringFilterInput}.'' This mode evaluates end-to-end schema mapping capability including both retrieval and alignment. Retrieval mode is appropriate when the target must be discovered from a catalogue at query time.

The distinction is important because retrieval mode is strictly harder, as errors in schema retrieval propagate to field-level mapping. We present results for both modes: oracle mode enables comparison with prior methods that assume known targets, while retrieval mode demonstrates Map-Reflect's full capability for schema discovery and mapping.

\textbf{OMOP API accuracy.} All OMOP datasets have a single fixed target (the OMOP Common Data Model). For most methods, API-level accuracy mainly reflects utterance parsing given a fixed target pool; LLM-based methods without product disambiguation can fail here (AnyTool Granite scores 0\% on all three, cf.\ Table~\ref{tab:type_results} footnote). The meaningful comparison is field-level F1, which ranges from under 14\% (GNN) to 100\% (Map-Reflect Llama on Synthea).

\textbf{ToolBench scores are high by dataset design.} ToolBench (3,190 samples) evaluates REST API schema mapping where oracle utterances explicitly name both source and target, making API-level identification straightforward, similar to OMOP. Field-level F1 (95--100\%) is also high because ToolBench APIs have well-documented parameter descriptions enabling direct lexical matching. ITOpsGraph (521 samples, 12 heterogeneous products, domain-specific terminology) is the harder evaluation.

\textbf{RAG content and leakage.} RAG-enhanced descriptions are generated from product documentation \emph{within each product's corpus only}. Descriptions for Turbonomic fields are derived from Turbonomic manuals; they do not reference Concert, Instana, or other target schemas. Cross-product mapping knowledge comes solely from the LLM's reasoning over schema structure and semantics, not from leaked target names in descriptions.

\textbf{SchemaNet Results.} Tables~\ref{tab:schemanet_type}--\ref{tab:schemanet} report per-dataset results on SchemaNet using Llama-3.3-70B only; Granite-4 produced near-zero scores across all schema pairs and is omitted because SchemaNet's multi-table relational reasoning exceeds the capacity of the smaller model. Map-Reflect (Llama) is essentially tied with AnyTool on type-level F1 and trails it narrowly on field-level F1, while substantially outperforming MatchMaker and GNN on both metrics. Retrieval mode incurs a large drop on the OMOP-target pairs because all five share the same target type pool, making retrieval ambiguous; schema pairs with unique targets (bank1\_bank2, imdb\_sakila) show no degradation. The GNN's high type accuracy on cprd\_gold\_omop reflects unusually regular naming in that pair rather than generalizable reasoning.



\section{Discussion}
\label{sec:discussion}

\subsection{Oracle vs.\ Retrieval Mode Analysis}

In oracle mode, UQ-triggered reflection preserves accuracy where the model is already confident and improves it where genuine uncertainty exists, confirming the selectivity of the UQ gate. On OMOP, Map-Reflect outperforms MatchMaker without requiring ColBERT-v2 preprocessing or DSPy~\cite{khattab2023dspy} bootstrapping. MatchMaker abstention rates are substantial across all datasets; all field F1 figures count abstentions as incorrect.

Retrieval mode presents additional challenges: the system must first discover appropriate target schemas from a catalogue via embedding-based retrieval. Errors in schema retrieval propagate to field-level mapping, making retrieval mode strictly harder than oracle mode in the general case.

\textbf{100\% API accuracy in retrieval mode reflects dataset characteristics.} The retrieval mode API accuracy of 100\% on ITOpsGraph and OMOP (Table~\ref{tab:type_results}) reflects dataset characteristics rather than trivial retrieval. ITOpsGraph contains only 12 products in the target pool; given a source utterance with strong embedding similarity, the retrieval top-$k$ reliably includes the correct target. OMOP datasets have a single fixed target schema (the OMOP CDM), so retrieval reduces to confirming the source schema against a known target. These constrained pools make API-level retrieval tractable even when field-level mapping remains challenging. SchemaNet retrieval (Table~\ref{tab:schemanet_type}) shows the opposite extreme: all five OMOP-target pairs share the same pool of OMOP target types, so the retrieval system cannot distinguish which OMOP tables are relevant to a given source schema. This ambiguity drives the large oracle-to-retrieval gap, concentrated in the OMOP pairs. Schema pairs with unique targets in the catalogue show no degradation.

\textbf{Retrieval mode field F1 is lower than oracle on most datasets.} Retrieval errors propagate to field-level mapping, and oracle mode includes all ground-truth pairs including cross-paradigm mappings. NL2GQL is an exception where retrieval slightly exceeds oracle, arising from selection bias: retrieval succeeds on semantically similar pairs that are also easier to map at the field level.

\textbf{Hyperparameter sensitivity.} Varying $\tau_H$ by ${\pm}0.1$ around its validation-tuned value has negligible effect: MAP-phase entropy is bimodal, with confident fields near zero and uncertain fields near the uniform maximum, so a wide range of thresholds produces the same binary gate decision. The signal-on/off sweep in Table~\ref{tab:ablation_components} captures the practically meaningful design dimension.

\textbf{Signal contributions.} The main result is about what \emph{hurts}. Error-triggered reflection causes the largest degradation, neighbourhood-triggered the next, and unconditional self-reflection the smallest, because these signals fire on predictions that were already correct, introducing false positives the LLM then over-corrects. Combining error with any other signal compounds the damage. UQ-triggered reflection is the sole safe default: it fires zero reflections when the model is uniformly confident and acts selectively where genuine uncertainty exists, operating precisely where the consistency hypothesis~\cite{xiao2025consistency} predicts it should.

On ITOpsGraph, error-triggered reflection reduces field recall by 14.9\,pp, neighbourhood-triggered by 7.1\,pp, and unconditional self-reflection by 5.4\,pp---all below the no-reflection baseline. Several combinations perform near the worst single-signal result. The full three-signal system reaches only 73.3\%. UQ-triggered reflection is the only configuration that does not reduce accuracy, because it fires only when entropy over candidate confidences exceeds $\tau_H$---when confidence is genuinely dispersed rather than concentrated on one target.

\textbf{OMOP Ablation: Dataset-Dependent UQ Effect.} Table~\ref{tab:ablation_omop} shows that UQ benefit is highest where the model has moderate initial confidence (MIMIC), and lowest where it is uniformly confident (Synthea). Even on Synthea, UQ degrades performance by far less than any other signal, confirming it as the safest default. Synthea has only 12 samples; the CMS and MIMIC results are stronger evidence.

\subsection{Error Analysis}
\label{sec:error_analysis}
Map-Reflect achieves high API accuracy on ITOpsGraph but lower field F1, meaning that even when the correct source--target pair is identified, a fraction of fields is incorrectly mapped. We identify three recurring failure modes from manual inspection of errors.

\textbf{Semantic synonym misses.} ITOpsGraph contains many cases where semantically equivalent fields carry entirely different names across products. For example, a field named \texttt{severity} in one product corresponds to \texttt{criticalityLevel} in another, or \texttt{hostName} to \texttt{nodeIdentifier}. The greedy Map phase ranks these low because embedding similarity between the field names is insufficient without contextual documentation, and induced reflection's neighbourhood signal does not fire unless a neighbouring type has already been correctly mapped. RAG-enhanced descriptions mitigate this for the 11,110 fields that have been enriched, but the remaining fields in the catalogue have sparse descriptions and account for a disproportionate share of failures.

\textbf{Schema paradigm boundary failures.} ITOpsGraph spans both GraphQL and proto buffer schemas. Fields that are modelled as nested object types in GraphQL (e.g., \texttt{VirtualMachine.resourceAllocation.cpuMhz}) appear as flat repeated fields in proto buffer definitions. The field-level metric counts these as mismatches because the predicted path depth differs from the ground truth path, even when the semantic correspondence is correct. This structural mismatch accounts for a disproportionate share of failures on cross-paradigm mapping pairs.

\textbf{Many-to-many boundary disagreements.} For types such as \texttt{Alert}, \texttt{Incident}, and \texttt{Event}, which are legitimate many-to-many mapping targets, SME-validated ground truth includes multiple valid target fields. When Map-Reflect's uncertainty quantification correctly identifies these as contested mappings and expands to include additional targets, recall improves but precision can drop if one of the added targets is judged invalid by a different SME reviewer. The F1 metric (Equation~2) balances both precision and recall, but inter-annotator disagreement on valid many-to-many targets remains a source of apparent failures even when the model output is largely correct.

Both failures trace to data quality and structural mismatch, not to the reflection mechanism itself. Enriching documentation coverage and adopting path-normalisation before field-level evaluation are the most direct remedies.

\subsection{Many-to-Many Field Mapping}
\label{sec:many_to_many}

The greedy MAP phase ranks target candidates for each source field independently.
When a source type has more fields than the target type, multiple source fields
may claim the same target field---a \emph{collision}. For example, mapping
\texttt{concert.Application} (22~fields) to \texttt{instana.ApplicationPerspective}
(6~fields) produces 68~collisions on ITOpsGraph, with 10~source fields all mapping
to \texttt{label} and 5~to \texttt{id}.

\textbf{Constrained assignment.}
We implemented a constrained assignment post-processing step (Phase~3.5) that
enforces one-to-one field mapping via greedy assignment with preemption: the
highest-confidence source field claims each target; displaced fields fall to their
next-best candidate. Fields with no viable alternative are marked as unmatched.

The drop is proportional to the number of legitimate many-to-one mappings in the

On ITOpsGraph the drop is modest ($-1.7$\,pp) because most collisions there are
genuine ambiguity rather than legitimate many-to-one.

\textbf{Many-to-one is legitimate in schema mapping.}
Unlike entity resolution where each mention refers to exactly one entity, schema
mapping inherently involves many-to-one relationships: multiple source columns may
join to the same target foreign key, several source attributes may represent facets
of one target concept, and standardised schemas like OMOP deliberately consolidate
proprietary fields into shared columns. Enforcing one-to-one at the field level
breaks these patterns.

\textbf{Recommendation.}
The base configuration (no constraint) with UQ-triggered reflection is the recommended
default.  Constrained assignment is available as an optional mode
(\texttt{-{}-constrained-assignment}) for downstream consumers that require strictly
deduplicated mappings, such as schema federation engines or query rewriters where
duplicate column bindings break join semantics.

\subsection{Limitations}

\textbf{UQ implementation and calibration.}
The confidence scores $\{\gamma_j\}$ used in the entropy trigger are prompt-elicited probabilities: the LLM is asked to score each candidate field on a 0--1 scale, and the scores are normalised to sum to 1 over the top-$n$ candidates. This differs from the pairwise-similarity aggregation in SIMBA~\cite{simba2025}, which computes confidence from agreement across multiple independent samples. Our entropy-H trigger is a single-pass approximation that avoids the cost of repeated sampling but does not directly implement the SIMBA aggregation.

The consistency hypothesis~\cite{xiao2025consistency} provides theoretical motivation (correct predictions concentrate probability mass; uncertain ones spread it), but we have not performed a formal calibration analysis (e.g., expected calibration error or risk-coverage curves) to verify that $H$ is well-calibrated as a confidence proxy. Additionally, the UQ gains are small in absolute terms (+0.2\,pp on ITOpsGraph, +1.7\,pp on OMOP-MIMIC, zero on NL2GQL); the primary claim is that UQ-triggered reflection is the only trigger that does not degrade accuracy, not that it yields large improvements.

\textbf{Small-dataset robustness.}
OMOP-Synthea has only 12 samples, OMOP-CMS 38, and OMOP-MIMIC 46. All LLM calls are deterministic (temperature~0, seed~42), so variance reflects dataset composition, not stochastic inference. On 12-sample Synthea a single wrong mapping shifts field F1 by $\sim$8\,pp; Synthea results are therefore illustrative. CMS and MIMIC ($n=38$, $n=46$) are the primary evidence for OMOP conclusions.

\textbf{Retrieval-mode evaluation at limited scale.}
The target pools in our retrieval-mode evaluation are small: ITOpsGraph has 12 products and OMOP has a single fixed target schema, making API-level retrieval tractable even with a basic dense retrieval setup. These constrained settings do not stress-test schema discovery at the scale of real enterprise catalogues, which may contain hundreds of products with semantically overlapping schemas. We report the SchemaNet retrieval results as a harder case (five OMOP-target pairs sharing the same pool causes substantial confusion), but a systematic evaluation with increasing catalogue size and hard distractors remains future work.

\textbf{Neighbourhood and error signal design.}
The neighbourhood and error signals use fixed penalty schedules and manually chosen thresholds ($g > 0.2$, error penalties of $-0.10$ to $-0.40$, $\eta = 0.05$). The ablation shows these signals consistently degrade accuracy by firing on correct predictions, but we do not explore whether learned or adaptive thresholds, such as a small classifier trained to predict when a signal is reliable, could recover their utility. The signals capture genuine structural information (neighbourhood consistency, known error patterns); the problem is their false-positive rate under fixed thresholds, not the information itself. Learned gating over these signals is the most direct path to making them useful.

\textbf{Baseline adaptation.}
Since much of the literature focuses on API sequencing or schema matching, we have had to adopt these baselines to our problem setting. Both AnyTool and MatchMaker are adapted from their original settings to enable comparison. AnyTool's three-tier hierarchy is rebuilt around our schema catalog rather than RapidAPI's taxonomy, and its GPT-4 backbone is replaced with Llama-3.3-70B and Granite-4-small. MatchMaker's ColBERT-v2 index and DSPy bootstrapping loop are retained, but the backbone is similarly replaced. These adaptations are necessary to isolate methodological differences from model-tier effects, but they mean the baselines are not operating under their best-known configurations. Additionally, several LLM-based schema matching systems (LSM~\cite{zhang2023schema}, Magneto~\cite{liu2024magneto}, ReMatch~\cite{sheetrit2024rematch}) are discussed in related work but not included experimentally; implementing them under matched conditions would provide a more complete comparative picture.

\textbf{Many-to-many scoring in ablations.}
The signal ablation (Table~\ref{tab:ablation_components}) evaluates a one-prediction-per-field variant with precision held constant at 86.2\%, so that recall variation directly measures each signal's effect without F1 confounding. The full Map-Reflect system uses score-threshold pruning ($\tau = 0.5$) to produce many-to-many mappings, and main results in Tables~\ref{tab:type_results}--\ref{tab:field_results} use this configuration. However, we do not report a separate set-based precision/recall breakdown that isolates how well the system identifies the complete set of valid targets for genuinely many-to-many fields. Such an evaluation would require richer per-field ground truth annotations specifying which targets are \emph{all} valid, beyond what the current SME-validated wiki provides.

\section{Conclusion}

Schema mapping across heterogeneous enterprise APIs and databases is a prerequisite for data federation, tool composition, and agentic workflows, yet it has received less attention than the downstream tasks it enables. Map-Reflect addresses this gap by framing the problem as induced reflection: a greedy Map phase produces an initial alignment, and a Reflect phase refines it selectively using external signals rather than unconditional self-critique. The central finding is that signal quality matters more than reflection itself. Error- and neighbourhood-based triggers degrade accuracy by firing on correct predictions; only uncertainty quantification identifies the cases where reflection genuinely helps. This selectivity is what makes the framework practical at enterprise scale, where reflection overhead must be justified by measurable improvement. The evaluation spans REST APIs, GraphQL, and relational databases across six benchmarks including a new Spider-derived benchmark with 745~foreign-key mappings across 164~databases, and the ITOpsGraph benchmark contributes a new resource for many-to-many API schema mapping grounded in SME-validated ground truth. Our analysis of constrained one-to-one assignment shows that many-to-one field mappings are legitimate in schema mapping---enforcing deduplication reduces field F1 by up to 46.5\,pp on OMOP-Synthea---confirming that the base many-to-many configuration is the correct default. More broadly, the result that unconditional self-reflection can hurt generalises beyond schema mapping to any tool-using agent that revises its own outputs without external grounding.
