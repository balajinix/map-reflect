\begin{abstract}
Schema mapping is the task of aligning database tables, API endpoints, and GraphQL types together with their fields across heterogeneous schemas. It is a prerequisite for data federation, function calling, and agentic tool composition. LLM-based approaches increasingly use reflection to improve mapping quality, but a key open question is \emph{when} reflection helps and when it hurts. We show empirically that most reflection triggers degrade accuracy: structural signals and heuristic error detectors fire on already-correct predictions and cause the model to over-correct. Only uncertainty-guided reflection consistently avoids this degradation, making it the safe default across diverse benchmarks. We introduce Map-Reflect, an \emph{gated reflection} framework that operationalises this finding. Map-Reflect is schema-agnostic and works with REST APIs, GraphQL, and relational databases. It supports runtime target discovery without elaborate offline pre-processing and runs with open-source models. We also introduce ITOpsGraph and ITOpsGraph-MB, the first benchmarks for enterprise API schema mapping with heterogeneous paradigms (GraphQL and proto buffer) and human-annotated many-to-many ground truth, filling a gap that existing relational benchmarks cannot address.
\end{abstract}

\section{Introduction}
\label{sec:intro}
Organizations rely on diverse API ecosystems and databases that must be integrated for effective data access. Schema mapping~\cite{matchmaker, liu2024magneto, sheetrit2024rematch, buss2025scalableschemamappingusing}, is the task of identifying equivalent entity types across different schemas, and is critical for building unified data access layers that allow querying across heterogeneous sources without knowledge of the underlying schema differences. This matters for AI agents and tool-calling scenarios~\cite{wang2024llmagent}, where LLMs must select and invoke APIs across multiple services.

    \centering
    \includegraphics[width=0.9\columnwidth]{intro_diagram.png}
    \caption{Map-Reflect pipeline: greedy MAP followed by signal-driven REFLECT.}
    \Description{Map-Reflect pipeline showing User Utterance flowing through Schema Retrieval, MAP Phase, REFLECT Phase with three signals (Neighbourhood Graph, Error Analysis, Uncertainty Quantification), and outputting Many-to-Many Mapping Set.}
    \label{fig:pipeline}
\end{figure}

Traditional approaches focus on database integration with column-level mapping, but enterprise environments require schema retrieval and multi-faceted mapping across both APIs and databases. For example, Site Reliability Engineers managing hybrid cloud environments must query across multiple observability platforms, each with distinct schemas. Mapping across these disparate systems creates substantial overhead.

\paragraph{The Many-to-Many Challenge.}
Prior work on schema mapping focuses on one-to-one alignments~\cite{matchmaker, sheetrit2024rematch} or single-chain API sequencing~\cite{saha-etal-2024-sequential}. Real enterprise environments require \emph{many-to-many mappings} where multiple source types/fields correspond to overlapping target structures. For example, \texttt{Incident} from one system may correctly map to both \texttt{Alert} and \texttt{Event} in another. Greedy one-to-one mapping leaves too many elements unmapped, while naive approaches create spurious mappings that break query semantics. Many Large Language Models (LLM) based solutions for this problem use reflection. A key challenge for any reflection mechanism is knowing \emph{when} to reflect: firing unconditionally corrupts correct predictions, while a reliable trigger must identify genuinely uncertain cases. Uncertainty quantification provides this gate. As we show on diverse datasets, UQ-triggered reflection is the only trigger that does not reduce field recall; all other signals fire too broadly and over-correct predictions that were already correct.

Recent advances in tool calling with large language models show promise for API-related tasks. ToolLLM~\cite{toolllm} and AnyTool~\cite{anytool} focus on sequencing a single chain of calls; they do not address systematic alignment of schema elements across products, which is the prerequisite for variable mapping between function calls. Sequential function calling with variable mapping across APIs has been studied by~\citet{saha-etal-2024-sequential}, who introduce GraphQLRestBench and demonstrate that GraphQL schema representations are effective for encoding API response structure in LLM prompts for multi-step API sequencing. Self-reflection mechanisms in these approaches lack external grounding because the model critiques its own output without validation against external signals, potentially reinforcing errors~\cite{huang2024selfcorrect}. Further, AnyTool requires GPT-4, limiting practical applicability.

\paragraph{The Pre-processing Cost Problem.}
Schema inventories in enterprise deployments are never static: Data Fabric and Data Mesh implementations~\cite{blohm2024data,dehghani2022datamesh} grow through M\&A activity and SaaS onboarding; Backend for Frontend patterns~\cite{richardson2018microservices} require re-alignment every time a new upstream service is added; and agentic code tools such as Claude Code and Gemini CLI need schema mapping as a \emph{runtime} capability rather than a batch offline step. AnyTool~\cite{anytool} requires rebuilding a multi-vector index, a DSPy bootstrapping loop, and a three-tier agent hierarchy whenever schemas change, and reports 43.3 GPT-4 calls per query in its original setting. In our problem setting, we want to avoid such expensive pre-processing steps and also the dependence on frontier models.

Building a unified Data Access Layer (DAL) or a Common Data Model requires mapping schemas across both APIs and databases. Hence we evaluate on API datasets (ITOpsGraph, NL2GQL, ToolBench) and database schemas (OMOP, SchemaNet). Our ITOpsGraph benchmark provides schema mapping across heterogeneous enterprise APIs, featuring (i)~deeply nested type hierarchies, (ii)~domain-specific terminology where semantically equivalent concepts have different names, and (iii)~many-to-many mappings where a single source type correctly maps to multiple targets. Our wiki-based Subject Matter Expert (SME) annotation provides continuous ground truth refinement.

% FIX ISSUE_3: Added Mistral-Large-2 to the model list in the introduction
We introduce Map-Reflect, an \emph{gated reflection} framework that addresses the above limitations through a two-phase approach (Figure~\ref{fig:pipeline}). In the first \emph{Map} phase, we greedily find the best mapping for each source type and its fields. In the second \emph{Reflect} phase, we explore three candidate external signals to gate reflection: a \emph{neighbourhood graph} that validates mapping assumptions, \emph{error analysis} from schema deployment and query execution, and \emph{uncertainty quantification} that selectively targets genuinely ambiguous predictions. As the ablation in Section~\ref{sec:ablation} shows, only the UQ signal avoids degrading accuracy; the other two hurt by over-correcting correct predictions. Besides empirical evidence, we provide theoretical grounding for UQ as a reflection trigger based in the consistency hypothesis~\cite{xiao2025consistency} and SIMBA~\cite{simba2025}. Unlike AnyTool, which requires building a static GPT-4--driven three-tier hierarchy before any mapping can be performed, Map-Reflect operates with open-source models (Llama-3.3-70B, Mistral-Large-2, Granite-4-small) and additionally supports runtime target discovery from a live catalogue with no offline pre-processing.

Our contributions are as follows:
\begin{itemize}[noitemsep,topsep=2pt,leftmargin=*]
  \item \textbf{Empirical study of reflection triggers} for LLM-based schema mapping, showing that structural and heuristic signals degrade accuracy by firing on already-correct predictions, while only uncertainty-guided reflection avoids degradation across all evaluated benchmarks (Section~\ref{sec:ablation}).
  \item \textbf{Map-Reflect}, a two-phase gated reflection framework that operationalises this finding: a greedy Map phase produces an initial alignment and a UQ-gated Reflect phase refines it selectively. The framework is GPT-free, schema-agnostic across REST APIs, GraphQL, and relational databases, and supports runtime target discovery from a live catalogue with no offline preprocessing.
  \item \textbf{ITOpsGraph benchmark}: the first enterprise API schema mapping benchmark spanning multiple schema paradigms (GraphQL and proto buffer), 12 products, 11,110 RAG-enriched fields, and human-validated ground truth covering many-to-many mappings across heterogeneous naming conventions.
  \item \textbf{ITOpsGraph-MB benchmark}: the first human-annotated many-to-many schema mapping benchmark with bipartite field constraints, covering 786 type pairs and 3,030 field mappings across 12 enterprise products (Section~\ref{sec:itgraph_mb}).
\end{itemize}


\section{Related Work}

\paragraph{Classical Schema Matching.} Cupid~\cite{madhavan2001generic}, COMA~\cite{10.5555/1287369.1287422}, and iMAP~\cite{dhamankar2004imap} are representative systems from the classical schema matching literature~\cite{rahm2001survey}, combining linguistic, structural, and domain-specific similarity. However, these systems assume flat relational schemas and produce one-to-one correspondences, limiting applicability to nested API schemas with many-to-many relationships. Valentine~\cite{koutras2021valentine} provides a systematic benchmark comparing these techniques. Map-Reflect builds on multi-signal intuition but uses LLM-driven reasoning with externally grounded reflection.

DynaMap~\cite{mazilu2022schema} and SMUTF~\cite{zhang2025smutf} use dynamic programming and XGBoost classifiers respectively, but struggle with contextual relationships. API retrieval and sequencing have been addressed by embedding-based retrievers~\cite{li2023api,patil2023gorilla}, fine-tuned methods~\cite{toolllm}, graph-based approaches~\cite{mandal2024graph}, and GraphQL-based sequential function calling~\cite{saha-etal-2024-sequential}. Pre-LLM API mapping work includes document-based~\cite{lu2017learning}, knowledge graph~\cite{liu2023recommeding}, and GNN approaches~\cite{shao2022cross}.

    \label{fig:reflection_example}
\end{figure*}

ToolLLM~\cite{toolllm} introduced the ToolBench dataset with an API Retriever for natural language instructions. Toolformer~\cite{schick2023toolformer} shows that LLMs can learn to invoke tools via self-supervised training, motivating tool-use settings where schema mapping becomes necessary. AnyTool~\cite{anytool} incorporates self-reflection for reliability via a three-tier agent hierarchy (meta-agent $\rightarrow$ category-agents $\rightarrow$ tool-agents) built around RapidAPI's static category taxonomy, and is designed around GPT-4 function calling. The hierarchy cannot be transferred to a new API corpus without rebuilding the taxonomy from scratch. AnyTool's self-reflection has no external validation signals, which can reinforce errors~\cite{huang2024selfcorrect}. These approaches focus on API sequencing, not schema mapping. We evaluate AnyTool on all datasets using oracle-mode utterances that name both source and target schemas explicitly (Section~\ref{sec:results}).

\paragraph{LLM-Based Schema Mapping.} LSM~\cite{zhang2023schema} uses fine-tuned BERT encoders; Magneto~\cite{liu2024magneto} combines SLMs with LLM reranking; ReMatch~\cite{sheetrit2024rematch} and GraphRAGToolFusion~\cite{lumer2025graphragtoolfusion} add retrieval mechanisms. MatchMaker~\cite{matchmaker} introduced compositional LLM programs with zero-shot self-improvement via synthetic in-context demonstrations, but requires GPT-4 as backbone, targets only flat relational schemas, and relies on offline ColBERT-v2 multi-vector indexing plus DSPy~\cite{khattab2023dspy} bootstrapping before deployment, preprocessing costs that scale with schema size and must be repeated when schemas evolve. For many-to-many matching, LLMatch~\cite{wang2025llmatch} uses Rollup/Drilldown abstraction, while SCHEMORA~\cite{gungor2025schemora} combines BM25 and FAISS~\cite{johnson2019billion} retrieval. Both target relational schemas and require upfront schema restructuring.

\paragraph{Uncertainty Quantification for LLMs.}
Uncertainty quantification (UQ) approaches estimate the reliability of LLM outputs
and are increasingly recognised as essential for trusted AI systems~\cite{simba2025}.
An important category are \emph{black-box} methods, which rely only on model outputs
without internal access and are therefore robust to model upgrades and compatible with
proprietary APIs~\cite{xiao2025consistency,simba2025}.
A central line of black-box work uses generation \emph{consistency} as a proxy for
confidence: when a generated response is more different from others it is more likely
to be incorrect, so responses that are consistently similar are more likely to be
correct~\cite{lin2024generating,manakul2023selfcheck}.
Xiao et al.~\cite{xiao2025consistency} formalize this as the
\emph{consistency hypothesis}, introducing three statistical statements
(Sim-Correct, Sim-Separate, Sim-Any) and empirically verifying them across 8
benchmarks spanning QA, summarisation, and text-to-SQL.
The \emph{text-to-SQL} task, which is the closest analogue to schema field prediction, shows the strongest and most consistent signal across all three hypothesis variants.
Bhattacharjya et al.~\cite{simba2025} introduce SIMBA, a
Similarity-Based Aggregation framework that unifies and generalises consistency-based
UQ by viewing confidence as a learned or hand-designed function of pairwise
similarities between generations.
SIMBA demonstrates that classification over pairwise similarities (using random forests)
yields the best-calibrated confidence estimates, while the harmonic mean of similarities
outperforms the arithmetic mean for structured-output tasks.
Map-Reflect's UQ trigger is grounded directly in this framework: we use generation
consistency to detect when field mapping predictions are genuinely ambiguous and
selectively invoke reflection only for those fields.

\paragraph{Positioning.} Map-Reflect begins with greedy one-to-one mapping and explores three external signals for gated reflection. Retrieval is intentionally lightweight, using hybrid dense vector search~\cite{karpukhin2020dpr} and BM25~\cite{robertson2009probabilistic} lexical matching merged by Reciprocal Rank Fusion~\cite{cormack2009reciprocal}, because the Reflect phase corrects residual rank errors rather than requiring retrieval to be perfect. Of the three signals, only UQ-triggered reflection avoids degrading accuracy (Section~\ref{sec:ablation}), compared to AnyTool's unconditional self-reflection~\cite{anytool} which has no external validation. Map-Reflect is schema-agnostic across REST APIs, GraphQL, and relational databases, and we evaluate on both API corpora (ITOpsGraph, NL2GQL, ToolBench) and database schema benchmarks (OMOP, SchemaNet). New schemas require only parsing and optional RAG enrichment, with no graph construction, model training, or schema restructuring.


\section{Map-Reflect Framework}
\label{sec:mapreflect}

Our two-phase architecture is designed for the many-to-many mapping challenge. Map-Reflect is schema-agnostic: it handles REST APIs, GraphQL, and relational databases uniformly, operating at two levels regardless of schema paradigm. \textbf{Type-level mapping} identifies semantically equivalent entities — GraphQL types, REST resources, or database tables (e.g., \texttt{VirtualMachine} in one system maps to \texttt{EC2Instance} in another). \textbf{Field-level mapping} aligns constituent attributes within mapped type pairs — GraphQL fields, REST parameters, or database columns. The first phase (Map) performs greedy one-to-one mapping, which is fast but leaves many elements unmapped and may create spurious mappings. The second phase (Reflect) explores three candidate external signals for gated reflection: neighbourhood graph validation, error analysis, and uncertainty quantification. As the ablation in Section~\ref{sec:ablation} establishes, only UQ-triggered reflection should be used by default. Given API specifications or database schemas, Map-Reflect applies the two-phase mapping process.

Unlike GPT-4-centric tool agents, our components are invoked but never trained. A user utterance $u$ is processed in five stages. First, a context extractor splits $u$ into source and destination phrases by prompting a hosted chat model. Second, each phrase is embedded and queried against a Chroma vector index, yielding neighbourhoods $\mathcal{S}_{\mathrm{src}}$ and $\mathcal{S}_{\mathrm{dst}}$. Third, a reasoning call evaluates every pair in $\mathcal{S}_{\mathrm{src}}\times\mathcal{S}_{\mathrm{dst}}$, assigns a confidence $\gamma_0$, and produces justifications; this is the greedy Map phase. Fourth, the Reflect phase collects three external signals and induces reflection to refine mappings. Finally, mappings with scores below threshold $\tau_p$ are pruned, yielding many-to-many coverage. When the evaluation utterance already names both source and target schemas directly, the context extractor step is bypassed; the full five-stage pipeline applies in the runtime target discovery setting (Section~\ref{sec:retrieval_results}).

\subsection{Two-Phase Architecture: Map and Reflect}

\textbf{Phase 1: Map (Greedy One-to-One).} For each source type $T_s$ in the source schema, we compute embedding similarity with all types in the target schema and select the highest-scoring target type $T_t$ as the initial mapping. For each field $F_s$ in the mapped source type, we similarly select the best matching field $F_t$. This produces a fast one-to-one mapping with confidence scores, but leaves many types/fields unmapped and may create spurious mappings based on superficial similarity.

\textbf{Phase 2: Reflect (Uncertainty-Guided Refinement).} The Reflect phase selectively refines the greedy mapping using external signals: \emph{coverage analysis} identifies unmapped source and target elements, \emph{signal collection} gathers neighbourhood validation, error analysis, and uncertainty scores, \emph{gated reflection} explores alternative mapping targets for high-uncertainty elements, and \emph{spurious mapping removal} verifies one-to-many mappings and removes those that fail validation. Our ablation (Section~\ref{sec:ablation}) shows that of the three signals, only UQ-triggered reflection avoids degrading accuracy; error-based and neighbourhood-based signals fire too broadly, over-correct correct predictions, and are not recommended in the default configuration.

\subsection{Gated Reflection Mechanism}

Induced reflection refines mappings using external signals rather than model self-critique alone (Figure~\ref{fig:reflection_example}).

We induce reflection via three external signals:

\textbf{Signal 1: Neighbourhood Graph Validation.} For each candidate mapping $(s, t)$, we retrieve $k$-nearest neighbours from the graph store and validate whether neighbours of the source type also map to neighbours of the target type, whether alternative targets with similar structure exist, and whether any unmapped neighbours should be included. If neighbourhood evidence contradicts the greedy mapping, we add alternative mappings (achieving many-to-many coverage) or remove inconsistent ones.

\textbf{Signal 2: Error Analysis.} Before reflection, we analyse the greedy mapping's ranking for structural error patterns — product mismatch, foreign key misalignment, low confidence, and ambiguous top-2 predictions — and attempt to generate and deploy a unified schema, surfacing type conflicts and null query results. Detected patterns are passed to the reflection prompt.

\textbf{Signal 3: Uncertainty Quantification.}
Selective reflection requires knowing \emph{which} predictions are genuinely uncertain
rather than firing unconditionally.
The consistency hypothesis~\cite{xiao2025consistency} provides formal
justification: correct LLM generations are systematically more similar to other
generations than incorrect ones, a pattern that holds especially strongly for
structured-output tasks analogous to schema field prediction.
SIMBA~\cite{simba2025} operationalises this as a family of aggregation functions over
pairwise similarities between generations.

\textbf{UQ trigger (entropy-H).}
Let $\{\gamma_1,\dots,\gamma_n\}$ be the LLM-assigned confidence scores for the top-$n$
candidate field predictions produced in the MAP phase for a source field $f$.
We compute Shannon entropy $H = -\sum_j \gamma_j \log \gamma_j$ and trigger reflection
when $H > \tau_H$, where
\begin{equation*}
\tau_H = \max\!\bigl(0.25,\; \mu_H + 1.5\,\sigma_H\bigr),
\end{equation*}
with $\mu_H$ and $\sigma_H$ the mean and standard deviation of prediction entropy
across all MAP-phase candidates, computed adaptively per dataset on a held-out
validation split (20\% of training pairs, withheld before any hyperparameter search).
On ITOpsGraph the adaptive formula yields $\mu_H + 1.5\sigma_H = 0.175$, which falls
below the floor, so $\tau_H = 0.25$.
High entropy indicates dispersed confidence across candidates. Correct predictions tend to concentrate on one candidate, while uncertain predictions spread across multiple plausible targets. Entropy is a single-pass proxy for the generation-consistency signal in SIMBA~\cite{simba2025}. Empirically, the distribution is heavily right-skewed: across 1,429 fields on ITOpsGraph, 91.7\% have entropy $\le 0.15$ and the gate fires on only 1.0\% of fields (15/1,429), confirming that the threshold is robust and the mechanism imposes negligible overhead (Figure~\ref{fig:entropy_dist}). Empirical calibration further validates the gate: fields above $\tau_H$ have 20\% MAP accuracy versus 84\% for fields below it, and accuracy decreases monotonically across uncertainty quartiles (Q1: 95\%, Q2: 80\%, Q3: 68\%, Q4: 60\%), confirming that high entropy identifies genuinely difficult predictions rather than arbitrary ones.

High-uncertainty mappings trigger reflection to explore alternative mapping
targets that the greedy MAP phase missed, often because multiple targets are
semantically valid (many-to-many coverage opportunity).

\paragraph{Grounding.}
Xiao et al.~\cite{xiao2025consistency} show that correct LLM generations are more similar to each other than incorrect ones, with the effect strongest on structured-output tasks. SIMBA~\cite{simba2025} generalises this by aggregating pairwise generation similarities into calibrated confidence estimates. Our entropy-H trigger approximates this: high entropy (dispersed confidence) identifies the low-consistency regime where predictions are most likely to be wrong. The ablation (Table~\ref{tab:ablation_components}) confirms that error-based and neighbourhood signals reduce field F1 by 7--15\,pp, while UQ-triggered reflection does not.

Let $\gamma_r(s,t)$ be the confidence after reflection round $r$. Given an adjustment $\Delta_r(s,t)$ constrained to $[-1,1]$, scores are updated as
\begin{equation}
\gamma_{r+1}(s,t)=\operatorname{clip}(\gamma_r(s,t)+\eta\,\Delta_r(s,t),0,1),
\label{eq:update}
\end{equation}
where $\eta{=}0.1$ is a fixed step size. $\Delta_r(s,t)\in[-1,0]$ is negative when a signal fires and zero otherwise: the neighbourhood signal sets $\Delta_r = -(g - 0.2)$ when the neighbourhood consistency gap $g$ exceeds 0.2, where $g = 1 - |\mathcal{N}_k(s) \cap \mathcal{N}_k(t)| / |\mathcal{N}_k(s)|$ is the fraction of $k$-hop neighbours of the source type $s$ that do \emph{not} also neighbour the target type $t$ in the property graph; the error signal sums per-error penalties (source/target mismatch $-0.40$, foreign-key misalignment $-0.30$, low confidence $-0.10$, ambiguous top-2 $-0.10$); and the UQ signal sets $\Delta_r = -(H - \tau_H)$ when prediction entropy $H > \tau_H$. Mappings with scores below a pruning threshold $\tau_p$ are discarded; the final output is $\{(s,t,j,\gamma)\mid\gamma\ge\tau_p\}$ with $\tau_p{=}0.5$.

When a signal fires and $\gamma_{r+1}(s,t)$ falls below $\tau_p$, the mapping $(s,t)$ is
a candidate for replacement. Alternative targets are drawn first from the pre-computed
neighbourhood candidate pool built during Map-phase traversal
(Section~\ref{sec:mapreflect}); the next-highest-scoring target not yet assigned to $s$
is promoted and its score initialised to $\gamma_0$. If the neighbourhood pool is
exhausted, a fresh MAP-phase LLM call is issued with the rejected target $t$ explicitly
excluded from the prompt, directing the model to consider structurally distinct
alternatives. This ensures that score penalties drive genuine candidate replacement
rather than merely suppressing the existing mapping without substitution.

\section{ITOpsGraph Benchmark}
\label{sec:itopsgraph}

Existing schema mapping benchmarks focus on flat relational schemas
(OMOP, SchemaNet) or single-domain API corpora (ToolBench, NL2GQL).
None expose the combination of challenges that characterise real
enterprise integration: heterogeneous schema paradigms, deeply nested
type hierarchies, domain-specific terminology where semantically
equivalent concepts carry entirely different names across products,
and legitimate many-to-many mappings where a single source type
correctly aligns with multiple targets.
We introduce \textbf{ITOpsGraph}, an enterprise API schema mapping
benchmark built from production IT operations and cloud infrastructure
schemas, and \textbf{ITOpsGraph-MB}, a derived many-to-many mapping
benchmark with human-annotated bipartite field correspondences.
Both datasets and the annotation tooling are released at
\url{https://github.com/balajinix/map-reflect}.

\subsection{Schema Collection and Enrichment}

ITOpsGraph is built from two families of production schemas spanning
12 products across IT operations and cloud infrastructure:

\textbf{Observability products (GraphQL).}
We parse GraphQL SDL~\cite{graphql2021spec} from six products:
Instana (infrastructure monitoring), Turbonomic (resource optimisation),
Concert (AIOps platform), Cloudability (cloud cost management),
NS1 (DNS and traffic management), and Watsonx-Orchestrate (AI
workflow automation). GraphQL schemas expose deeply nested type
hierarchies with interface inheritance and union types.

\textbf{Cloud infrastructure tools (proto buffer).}
We parse Protocol Buffer~\cite{google2023protobuf} definitions from
five tools: AWS, Azure, and GCP cloud provider schemas, HashiCorp
Terraform (infrastructure-as-code), and HashiCorp Packer (image
building). Proto buffer schemas use flat repeated fields where
GraphQL uses nested objects, creating paradigm-boundary challenges
for cross-system mapping.

Parsing yields 1,640 types and 10,876 fields across the 12 products.
To enrich field descriptions, we convert 239\,MB of product
documentation (PDF manuals and API references) using
docling~\cite{auer2024docling} and index the resulting text in
ChromaDB~\cite{chromadb2023}. For each field, we retrieve the
three most relevant documentation passages and concatenate them
as a RAG-enriched~\cite{lewis2020retrieval} description. This
process surfaces an additional 234 fields referenced in
documentation but absent from the parsed schemas, bringing the
total to \textbf{1,640 types and 11,110 RAG-enriched field
descriptions}. The unified schema is loaded into a typed property
graph (Section~\ref{sec:nbr_graph}) and served through a
vector index (Milvus~\cite{wang2021milvus}) for retrieval.

\subsection{Neighbourhood Graph}
\label{sec:nbr_graph}

The neighbourhood graph is a property graph over the unified schema
that enables structure-aware candidate expansion during mapping.
We construct it using NetworkX~\cite{hagberg2008networkx} with three
weighted edge types:
same-type edges (weight 0.3) connect all fields within the same type;
cross-type edges (weight 0.7) connect fields across types within the
same product; and semantic edges connect fields across products when
their embedding similarity exceeds 0.8, weighted by the similarity score.
Each node carries four attributes: fully qualified name, parent type,
source product, and RAG-enriched description.

During the Map phase, after retrieving initial candidates via
dense-vector search, we expand the candidate set by traversing
$k{=}5$ hops from each retrieved candidate (chosen by grid search
over $\{2,3,5,7\}$ on a held-out validation split).
Neighbours are added to the candidate pool weighted by path distance,
surfacing semantically related fields that embedding similarity over
short identifier strings alone would miss.
Graph construction for the full 11,110-field schema takes
approximately 80 seconds on commodity hardware and is persisted
across mapping sessions.
During the Reflect phase, the graph is additionally queried to
validate neighbourhood consistency: if \texttt{TypeA} maps to
\texttt{TypeB}, neighbours of \texttt{TypeA} should also map to
neighbours of \texttt{TypeB}.

\subsection{Wiki-Based Schema Documentation}

We deploy a MediaWiki~\cite{mediawiki} instance organised hierarchically
by product, type, and field. Each product has a dedicated page
documenting its schema structure; type pages list constituent fields
with descriptions and usage notes; and bidirectional hyperlinks connect
semantically equivalent fields across products. The wiki currently
documents all 12 products, 1,679 types, and 11,110 field descriptions
with RAG-enhanced content. It serves two roles: a living documentation
resource that evolves as products change, and the interface through which
subject matter experts (SMEs) review candidate mappings before they are
promoted to ground truth.

\subsection{Human Annotation}
\label{sec:annotation}

Ground truth for both ITOpsGraph and ITOpsGraph-MB is produced through
human annotation. We developed a purpose-built Streamlit annotation
tool that presents each candidate type pair to the annotator alongside:
candidate field mappings from an ensemble of seven schema mapping methods
(Map-Reflect, MatchMaker, ReMatch, GNN, SMT, ReAct, UE-Reflect) across
multiple LLM backbones with per-method confidence scores and consensus
counts; and API field metadata including data type, fully qualified name,
and RAG-enriched description.

For each type pair the annotator makes two classes of decisions.
At the \textbf{type level}, the annotator assigns one of four
judgments: \emph{Correct} (the type mapping is semantically
equivalent), \emph{Plausible} (related but not strictly equivalent),
\emph{Incorrect} (the type mapping is wrong), or \emph{Uncertain}
(insufficient information to decide).
At the \textbf{field level}, the annotator accepts, rejects, or
corrects each candidate field mapping using a dropdown populated
from the target type's field list. The tool enforces a bipartite
constraint in real time: once a target field is assigned to a
source field, it is removed from the dropdown for all remaining
source fields, preventing duplicate assignments.

The ensemble methods serve solely as candidates to reduce cold-start
effort; the annotator makes all authoritative decisions independently.
Annotations are saved incrementally with timestamps and exported as
JSONL with full provenance.

\subsection{ITOpsGraph: One-to-One Evaluation Benchmark}

ITOpsGraph contains \textbf{521 evaluation samples} representing
cross-product type mapping tasks, each pairing a source type from
one product with a target type from another, with human-validated
field-level ground truth. The benchmark poses three challenges:

\begin{enumerate}[noitemsep,topsep=2pt,leftmargin=*]
  \item \textbf{Schema paradigm heterogeneity.} GraphQL nested object
    types become flat repeated fields in proto buffer; field path
    depths differ across paradigms.
  \item \textbf{Domain-specific terminology.} Semantically equivalent
    fields carry entirely different names:
    \texttt{severity} vs \texttt{criticalityLevel},
    \texttt{hostName} vs \texttt{nodeIdentifier},
    \texttt{Alert} vs \texttt{Incident} vs \texttt{Event}.
  \item \textbf{Legitimate many-to-one mappings.}
    Multiple source fields may correctly map to the same target
    field when a standardised schema consolidates proprietary fields.
\end{enumerate}

\subsection{ITOpsGraph-MB: Many-to-Many and Bipartite Benchmark}
\label{sec:itgraph_mb}

ITOpsGraph-MB evaluates the harder setting where one source API type
legitimately maps to multiple target types, and within each type pair
field mappings are bipartite: each target field is claimed by at most
one source field.
We first generate candidate type pairs by running an ensemble of seven
schema mapping systems on all cross-product type pairs across the 12
products, retaining pairs predicted by at least two method/model
combinations with at least two candidate bipartite field mappings.
All retained pairs are then validated through the human annotation
workflow (Section~\ref{sec:annotation}): the annotator reviews each
type pair, assigns a type-level judgment, and accepts, rejects, or
corrects each field mapping with the bipartite constraint enforced live.

The resulting \textbf{ITOpsGraph-MB} benchmark contains 786 human-validated
type pairs with 3,030 bipartite field mappings across 12 products.
To our knowledge, it is the first human-annotated benchmark for
many-to-many schema mapping with bipartite field constraints on
enterprise API schemas. Existing many-to-many benchmarks (SchemaNet,
SCHEMORA) target flat relational schemas with primary/foreign key
annotations; none span multiple schema paradigms or require expert
judgment on cross-product naming divergence at this scale.

A GNN baseline trained on the full ITOpsGraph-MB graph (1,148 type pairs,
12,879 nodes) using GraphSAGE~\cite{hamilton2017inductive} with link
prediction provides a structural upper bound for comparison.

\section{Experiments}

We compare Map-Reflect against three baseline approaches. The \textbf{GNN} baseline uses a two-layer Graph Convolutional Network~\cite{kipf2017gcn} with 128-dimensional embeddings trained on ITOpsGraph pairs and evaluated zero-shot on all other datasets, except Spider where a separate GNN is trained on the Spider FK graph (Section~\ref{sec:results}). \textbf{AnyTool}~\cite{anytool} represents hierarchical retrieval with self-reflection via a static GPT-4--driven three-tier taxonomy; we re-implement with the same Llama-3.3-70B and Granite-4 backbones and evaluate with oracle-mode utterances naming both source and target schemas explicitly. This matched-backbone policy isolates methodological differences from backbone effects; AnyTool's best-case performance with GPT-4 would likely exceed our reported numbers on tasks where GPT-4's stronger reasoning matters. \textbf{MatchMaker}~\cite{matchmaker} is a compositional LM program with zero-shot self-improvement via ColBERT-v2 retrieval and DSPy bootstrapping; it requires two offline preprocessing steps before deployment and evaluates only on flat relational schemas in its original paper. In the ablation, the configuration using only the UQ trigger corresponds to the recommended default.

\textbf{Omitted Baselines.} We do not compare against SCHEMORA~\cite{gungor2025schemora}, a recent many-to-many schema matching method that targets flat relational schemas and requires upfront column-group normalization that assumes tabular input with explicit primary/foreign key annotations. Our benchmarks include deeply nested API schemas where this restructuring step does not apply, and SCHEMORA's code release is pending. We include MatchMaker~\cite{matchmaker} because it has public code and evaluation on the same OMOP and SchemaNet benchmarks. LLMatch~\cite{wang2025llmatch} reports SchemaNet results using field-level F1; aggregate comparisons appear in Tables~\ref{tab:type_results}--\ref{tab:field_results}.

Map-Reflect uses ChromaDB~\cite{chromadb2023} with sentence-transformer embeddings (\texttt{all-MiniLM-L6-v2}~\cite{reimers2019sentence}) for vector indexing and LLM calls via WatsonX~\cite{ibm2023watsonx} for core mapping logic. The UQ entropy threshold is computed adaptively as $\tau_H = \max(0.25,\, \mu_H + 1.5\sigma_H)$ with no dataset-specific tuning. All LLM calls use temperature~0 and a fixed random seed (42) for reproducibility.

We evaluate all methods using three LLMs: \textbf{Granite-4}
(\texttt{ibm/granite-4-h-small})~\cite{granite2025}, a smaller open-source model;
\textbf{Llama-3.3-70B} (\texttt{meta-llama/llama-3-3-70b-instruct})~\cite{grattafiori2024llama3},
providing stronger reasoning; and \textbf{Mistral Medium 25.05}
(\texttt{mistralai/mistral-medium-2505}), a large open-weights model.
All models are accessed via WatsonX~\cite{ibm2023watsonx}.
In the tables, ``Granite'' refers to Granite-4, ``Llama'' refers to Llama-3.3-70B,
and ``Mistral'' refers to Mistral Medium 25.05.
For fair comparison, all LLM-based baselines (AnyTool, MatchMaker) use the same model versions; the original AnyTool paper~\cite{anytool} used GPT-4, but we re-implement with Llama-3.3-70B and Granite-4 to isolate methodological differences. MatchMaker also uses ColBERT-v2~\cite{colbert} (\texttt{colbert-ir/colbertv2.0}) for candidate retrieval. The original MatchMaker paper uses GPT-4 (0613) at temperature~0.5; our reimplementation uses the same Llama-3.3-70B and Granite-4 backbones as all other baselines.

\subsection{Datasets}

We evaluate Map-Reflect on API and database schema mapping datasets representing diverse real-world scenarios:

\textbf{ToolBench Dataset}: We utilize the ToolBench dataset containing 49,937 REST APIs across 10,388 tools spanning 50 categories. For evaluation, we process the first 10,000 training queries and retain the 3,190 queries that involve at least two distinct APIs with overlapping parameter types, forming API mapping examples where each query-API pair generates variable mappings depending on functional similarities detected by the model. Queries involving only a single API (no cross-API mapping) are excluded.

\textbf{ITOpsGraph and ITOpsGraph-MB}: Enterprise API schema mapping benchmarks introduced in Section~\ref{sec:itopsgraph}. ITOpsGraph contains 521 evaluation samples across 12 products with human-validated field-level ground truth. ITOpsGraph-MB extends this to 786 many-to-many type pairs with 3,030 human-annotated bipartite field mappings.

\textbf{NL2GQL Dataset}~\cite{kesarwani-etal-2024-graphql}: Natural language to GraphQL API schema mapping dataset featuring e-commerce, social media, and content management system schemas. The dataset contains 437 mapping instances with varying complexity levels from simple field mappings to complex relationship transformations, testing systems' ability to handle domain-specific terminology across 54 GraphQL API schemas.

\textbf{OMOP Datasets}: We evaluate on three healthcare database schema mapping benchmarks derived from the OMOP Common Data Model~\cite{omop,garza2016omop,hripcsak2015ohdsi}: (i) \textbf{CMS} (Centers for Medicare \& Medicaid Services claims data), (ii) \textbf{MIMIC}~\cite{johnson2016mimic} (Medical Information Mart for Intensive Care), and (iii) \textbf{Synthea}~\cite{walonoski2018synthea} (synthetic patient data). These datasets test mapping between proprietary healthcare data formats and the standardized OMOP schema, featuring challenges such as vocabulary mapping (ICD codes~\cite{who2019icd10} to SNOMED~\cite{snomed2021}), temporal alignment, and cardinality differences. Unlike API mapping, database schema mapping involves relational constraints and referential integrity.

\textit{Ground Truth Protocol.} The OMOP ground truth mappings are derived from the OMAP benchmark~\cite{matchmaker}, which provides expert-curated field-level correspondences between source schemas (CMS, MIMIC, Synthea) and the OMOP CDM target schema. We follow the evaluation protocol of prior work~\cite{matchmaker}: evaluation utterances specify both source and target schemas (e.g., ``map MIMIC PATIENTS to OMOP PERSON''), reflecting the typical use case where healthcare organizations know they want to map their proprietary data to the OMOP standard. Since OMOP is the single standardized target, target discovery is not needed for these benchmarks.

\textbf{Spider Dataset}~\cite{yu2018spider}: We derive a schema mapping benchmark from Spider~1.0, a text-to-SQL dataset containing 166~databases with expert-defined foreign key relationships. Each foreign key defines a joinable column pair between two tables; we extract all 745~unique table pairs (793~field-level mappings) across 164~databases as evaluation samples. Unlike other benchmarks that provide mapping utterances, Spider's ground truth is structural (foreign keys), testing whether methods can discover joinability from schema structure alone. The mapping utterance is generated as ``map~\texttt{<source\_table>}~data to~\texttt{<target\_table>}~data.'' Spider is the largest and most diverse relational benchmark in our evaluation, spanning domains including music, flights, pets, cars, healthcare, and education.

\textbf{SchemaNet Dataset}~\cite{wang2025llmatch}: A relational database schema matching benchmark covering seven schema pairs of varying complexity (377 total mappings): bank1\_bank2, imdb\_sakila, and five OMOP target pairs (cms\_omop, mimic\_iii\_omop, synthea\_omop, cprd\_gold\_omop, cprd\_aurum\_omop~\cite{herrett2015cprd}). The OMOP pairs overlap structurally with our OMOP evaluation but use different source schemas and ground truth; results are therefore reported separately. SchemaNet tests purely relational schema alignment without API or graph paradigms, providing complementary coverage to the API-focused benchmarks.

\subsection{Evaluation Metrics}

We evaluate schema mapping using two complementary metrics that capture both API-level selection and field-level mapping quality (Figure~\ref{fig:api_field_gap} visualises the gap between them across all methods and datasets).

\textbf{API-Level (Product) Accuracy} measures whether the correct source and target schemas are identified by the method. A mapping is API-correct if predicted source and target match expected schemas (case-insensitive):
\begin{equation}
\text{API Acc.} = \frac{|\{s : \text{pred}(s) = \text{exp}(s)\}|}{|\text{Samples}|}
\end{equation}

\textbf{Field-Level F1 (Given Correct API)} measures property mapping quality \emph{only on samples where API selection was correct}, isolating field mapping quality from API selection errors. We compute precision, recall, and their harmonic mean:
\begin{equation}
P = \frac{|\text{Pred} \cap \text{GT}|}{|\text{Pred}|}, \quad
R = \frac{|\text{Pred} \cap \text{GT}|}{|\text{GT}|}, \quad
\text{F1} = \frac{2 \cdot P \cdot R}{P + R}
\end{equation}
where Pred and GT are the sets of predicted and ground-truth field mappings across all API-correct samples.

For semantic assessment, we use cosine similarity with sentence-transformer embeddings~\cite{reimers2019sentence} (threshold 0.3).

\textbf{ITOpsGraph-MB field accuracy} is micro-averaged over all ground-truth field mappings across the 786 type pairs: $\text{Acc} = |{\rm Pred} \cap {\rm GT}| / |{\rm GT}|$, where the bipartite constraint (each target field claimed at most once) is enforced during prediction but not during scoring — a predicted mapping is correct if it appears in the human-annotated ground truth regardless of whether it is the only source claiming that target.

\textbf{Efficiency.} Map-Reflect issues 1--2 LLM calls per source field: one MAP reasoning call, and one REFLECT call only where the UQ gate fires. On ITOpsGraph the gate fires on 1.0\% of fields (15/1,429 fields; median 1.0 call/field, max 2). On NL2GQL and ToolBench the gate fires zero times (1.0 call/field uniformly). On OMOP the gate fires on 28--45\% of fields (median 1.3--1.5 calls/field) but produces minimal accuracy change, confirming the calls are low-value overhead. AnyTool reports 43.3 GPT-4 calls per query in its original setting~\cite{anytool}, representing an order-of-magnitude higher inference cost even before accounting for the stronger backbone.

\subsection{Results: Gated Reflection for Field Mapping}
\label{sec:results}

Tables~\ref{tab:type_results} and~\ref{tab:field_results} compare Map-Reflect against MatchMaker, GNN, AnyTool, and LLMatch (where applicable). All methods are evaluated with utterances specifying both source and target schemas.

Map-Reflect achieves the highest field F1 on ITOpsGraph (87.7\%) and perfect API accuracy on all OMOP datasets. UQ-triggered reflection adds +0.2\,pp over the no-reflection base on ITOpsGraph; on NL2GQL it fires zero times because the model is uniformly confident, while unconditional self-reflection reduces field F1 by 5.4\,pp. On NL2GQL, MatchMaker Granite achieves higher per-API field F1 than Map-Reflect but selects the correct API on fewer than 60\% of samples, trading coverage for precision.

Map-Reflect outperforms both MatchMaker and AnyTool on field F1 across all three OMOP datasets.\footnote{OMOP-Synthea has only 12 evaluation samples.} AnyTool achieves 60.5\% field F1 on CMS, 49.5\% on MIMIC, and 72.3\% on Synthea, versus Map-Reflect Mistral at 77.2\%, 64.7\%, and 97.0\%. Backbone choice matters: Llama-3.3-70B outperforms Granite-4 consistently on field F1.

\textbf{Spider.} Spider has structural ground truth (foreign key relationships) and utterances that do not name the target schema, making it the most open-ended retrieval setting. For this benchmark, we train a separate GNN on the Spider FK graph using type-level \texttt{maps\_to} edges derived from foreign key relationships, rather than using the ITOpsGraph-trained GNN zero-shot. The GNN benefits from FK-derived training signal unavailable to zero-shot methods; its results are best understood as an upper bound on what structural supervision can achieve, not a directly comparable baseline. The GNN achieves 39.6\% type accuracy and a striking 77.6\% field F1. On type-level accuracy, Map-Reflect leads clearly---Mistral achieves 97.4\% and Llama 95.0\% versus AnyTool's 86.6\%, MatchMaker's best of 85.8\% (Granite), and the GNN's 39.6\%. The field-level ordering differs: AnyTool leads at 86.7\%, followed by MatchMaker Granite (85.8\%), Map-Reflect Mistral (81.9\%), and the GNN (77.6\%). AnyTool and MatchMaker both use retrieval mechanisms well-suited to lexically generic column names (\texttt{id}, \texttt{name}, \texttt{date}); ColBERT multi-vector matching and AnyTool's hierarchical search both benefit from column description overlap that embedding similarity over short identifiers cannot capture. Map-Reflect's UQ gate correctly identifies ambiguity among tables sharing identically-named foreign key columns but cannot resolve it without schema-level join path information absent from the utterance. Despite trailing on per-sample field F1, Map-Reflect identifies the correct table pair at a substantially higher rate; raw field recall over all 745 pairs favours Map-Reflect on both Llama and Mistral.

\textbf{SchemaNet.} Map-Reflect is essentially tied with AnyTool on type-level F1 (48.8 vs.\ 49.0) and trailing narrowly on field-level F1 (39.3 vs.\ 41.3), while substantially outperforming MatchMaker and GNN. Analysis is in Section~\ref{sec:schemanet_discussion}.

The gap is largest on NL2GQL (Llama 91.4\% vs AnyTool 16.4\% type F1) and ToolBench (Mistral 99.0\% vs 45.0\%) --- datasets where AnyTool's static three-tier hierarchy has no routing signal without a target hint. \subsection{When Reflection Fails}\label{sec:when_fails}

A central finding of this paper is that reflection is not universally beneficial — it is harmful by default and safe only when properly gated. We identify three mechanisms by which reflection degrades accuracy in schema mapping:

\textbf{Neighbourhood validation fires on correct predictions.} When a source type is correctly mapped, its neighbours are typically also mapped consistently. The neighbourhood signal computes a structural gap score and triggers reflection when the gap exceeds a threshold. On ITOpsGraph, this threshold is exceeded for many correctly-mapped pairs because the schema graph is heterogeneous enough that neighbourhood consistency is not a reliable indicator of error. The LLM, prompted to reconsider a correct prediction, produces an alternative that scores lower on the ground truth.

\textbf{Error heuristics conflate uncertainty with incorrectness.} The error signal fires on six lexical and structural patterns — low confidence scores, ambiguous top-2 candidates, type hint mismatches, and others. These patterns correlate with difficulty but not with error: a model can be appropriately uncertain (two candidates are genuinely close) without being wrong. Triggering reflection on these cases causes the model to swap a correct answer for a different one.

\textbf{Unconditional reflection amplifies the same error.} Self-reflection without an external signal prompts the model to critique its own output. On schema mapping, where the model's initial confidence is already well-calibrated on familiar domains, this leads to the same over-correction pattern: the model generates a rationale for a change that was not needed.

The consistent pattern across all three mechanisms is that reflection fires on predictions the model was already correct about. The ablation (Table~\ref{tab:ablation_components}) quantifies this: on ITOpsGraph, error-triggered reflection reduces field recall by 14.9\,pp, neighbourhood-triggered by 7.1\,pp, and unconditional self-reflection by 5.4\,pp. Only UQ-triggered reflection avoids this pattern because it fires only when the model's candidate distribution is genuinely dispersed — the precise condition where reconsidering the top candidate is likely to help.

This result generalises beyond schema mapping. Any LLM system that revises structured outputs using heuristic or structural signals risks degrading already-correct predictions. Uncertainty quantification is the minimal reliable gate.

\textbf{Hyperparameter sensitivity.} Varying $\tau_H$ by ${\pm}0.1$ around its effective value of $\tau_H = 0.25$ on ITOpsGraph has negligible effect: as Figure~\ref{fig:entropy_dist} shows, the MAP-phase entropy distribution is heavily right-skewed, with 91.7\% of fields below 0.15 and only 1.0\% above the threshold. \subsection{Error Analysis}
\label{sec:error_analysis}
Map-Reflect achieves high API accuracy on ITOpsGraph but lower field F1, meaning that even when the correct source--target pair is identified, a fraction of fields is incorrectly mapped. We identify three recurring failure modes from manual inspection of errors.

\textbf{Semantic synonym misses.} ITOpsGraph contains many cases where semantically equivalent fields carry entirely different names across products. For example, a field named \texttt{severity} in one product corresponds to \texttt{criticalityLevel} in another, or \texttt{hostName} to \texttt{nodeIdentifier}. The greedy Map phase ranks these low because embedding similarity between the field names is insufficient without contextual documentation, and gated reflection's neighbourhood signal does not fire unless a neighbouring type has already been correctly mapped. RAG-enhanced descriptions mitigate this for the 11,110 fields that have been enriched, but the remaining fields in the catalogue have sparse descriptions and account for a disproportionate share of failures.

\textbf{Schema paradigm boundary failures.} ITOpsGraph spans both GraphQL and proto buffer schemas. Fields that are modelled as nested object types in GraphQL (e.g., \texttt{VirtualMachine.resourceAllocation.cpuMhz}) appear as flat repeated fields in proto buffer definitions. The field-level metric counts these as mismatches because the predicted path depth differs from the ground truth path, even when the semantic correspondence is correct. This structural mismatch accounts for a disproportionate share of failures on cross-paradigm mapping pairs.

Both failure modes trace to data quality and structural mismatch, not to the reflection mechanism itself.

\subsection{Many-to-Many Field Mapping}
\label{sec:many_to_many}

The greedy MAP phase ranks target candidates for each source field independently.
When a source type has more fields than the target type, multiple source fields
may claim the same target field---a \emph{collision}. For example, mapping
\texttt{concert.Application} (22~fields) to \texttt{instana.ApplicationPerspective}
(6~fields) produces 68~collisions on ITOpsGraph, with 10~source fields all mapping
to \texttt{label} and 5~to \texttt{id}.

Enforcing one-to-one mapping via greedy preemption reduces these collisions but also reduces field F1 on every dataset with expert-curated ground truth, because many-to-one mappings are legitimate: multiple source fields may join to the same foreign key, represent facets of one target concept, or correspond to a standardised schema like OMOP that consolidates proprietary fields into shared columns. On OMOP-Synthea, where 29 source fields correctly map to the same OMOP CDM column, enforcing one-to-one drops field F1 from 100\% to 53.5\%; on ITOpsGraph the drop is a modest $-1.7$\,pp because most collisions there are genuine ambiguity rather than legitimate many-to-one. The base configuration (unconstrained with UQ-triggered reflection) is therefore the recommended default. A constrained mode (\texttt{-{}-constrained-assignment}) is available for downstream consumers such as schema federation engines or query rewriters where duplicate column bindings break join semantics.

\subsection{Limitations}

The UQ entropy trigger uses prompt-elicited confidence scores rather than the sampling-based aggregation in SIMBA~\cite{simba2025}; this is a single-pass approximation that avoids repeated inference but does not directly implement the theoretical framework we cite. UQ gains are modest (+0.2\,pp on ITOpsGraph, neutral on OMOP); the primary claim is that UQ is the only trigger that does not degrade accuracy. Retrieval-mode evaluation uses small target pools (12 products on ITOpsGraph; single fixed target on OMOP), so 100\% API accuracy there reflects dataset constraints rather than stress-tested discovery. MatchMaker results on ITOpsGraph-MB are limited to a 246-sample subset due to a missing retry mechanism in its agent framework. Larger retrieval catalogs with hard distractors remain future work.

\section{Conclusion}

Schema mapping across heterogeneous enterprise APIs and databases is a prerequisite for data federation, tool composition, and agentic workflows, yet it has received less attention than the downstream tasks it enables. Map-Reflect addresses this gap by framing the problem as gated reflection: a greedy Map phase produces an initial alignment, and a Reflect phase refines it selectively using external signals rather than unconditional self-critique. The central finding is that signal quality matters more than reflection itself. Error- and neighbourhood-based triggers degrade accuracy by firing on correct predictions; only uncertainty quantification identifies the cases where reflection genuinely helps. This selectivity is what makes the framework practical at enterprise scale, where reflection overhead must be justified by measurable improvement. The evaluation spans REST APIs, GraphQL, and relational databases across seven benchmarks including the ITOpsGraph benchmark for enterprise API schema mapping and ITOpsGraph-MB, the first human-annotated many-to-many benchmark with bipartite field constraints (786 type pairs, 3,030 fields, 12 products). Enforcing one-to-one field assignment substantially reduces F1 on healthcare benchmarks where standardised schemas consolidate proprietary fields, confirming that many-to-many is the correct default. More broadly, the finding that unconditional self-reflection degrades accuracy generalises to any tool-using agent that revises outputs without external grounding.
